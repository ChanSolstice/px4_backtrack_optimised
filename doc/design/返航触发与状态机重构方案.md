## 0. 摘要

本方案重构返航模块的触发处理和状态机，解决实飞中"低电量返航过程中失控后不再返航"一类组合触发问题，并把状态机整理为可验证、可维护的结构。核心变化：

1. 任一条件触发返航后，只运行一个返航任务；其余条件每个周期都评估，只记录和上报，不打断返航。
2. 暂停改为退出。退出后模块继续录制；退出后失控时，沿"截断后的轨迹 + 手动飞行段"返航，不直线拉回。
3. 链路丢失期间被外部切出 OFFBOARD 时，重新申请控制权。
4. 所有等待点都有超时，超时后按统一阶梯升级。
5. 状态转移只在状态机内部发生；状态机分为任务阶段、控制权、跟随方式三个并行区域；条件每周期全量评估；输出逐周期计算；轨迹规划移到后台线程，模式请求统一由 `ModeCommander` 发出并观察结果。
6. 固件屏蔽了 PX4 原生 RC 失控保护，失控帧在飞控看来仍是有效遥控输入（第 1.4 节）。接收机失控时摇杆回中，所以手动模式下失控表现为悬停；OFFBOARD 丢失时飞控切到 POSCTL，同样悬停（D10）。方案据此对 CH7 做逐帧门控。超时升级按"悬停优先"调整：返航无法继续时保持悬停，确认低电量才降落（D11）。
7. 实飞中"低电量后失控原地降落"的直接原因还没有确定，需要在 dev 上复现（第 1.4 节、FT0）。
8. 2026-10-20 按危害分析和闭环仿真复审，已按修改建议 M1–M7 修订（D22–D28），依据见[返航程序系统性分析](../reviews/返航程序系统性分析_2026-10-20.md)。
9. 增加可开启的调试日志（D29）：记录状态机三个区域的转换（带规则和原因）、飞控模式变化、模式请求结果等，路径可配置；按进程内的最小方案实现，不移植 `feat/return-diagnostics`（附录 C）。

审核中另外发现 4 项必须处理的问题：落地保护缺失、同步规划阻塞控制循环、电量无效值被当作低电量、重新申请控制权后的局部投影窗口。详见第 15 节；全部确认结论见第 17 节。

## 1. 背景与现状问题

### 1.1 实飞现象

### 1.4 固件前提与推论

**固件改动（用户提供）：**
- 在 `sbus_decode` 中把 `*sbus_failsafe` 强制置为 false，PX4 不再触发原生 RC 失控保护。
- 失控通过 CH18 传递，由 RK3588 上的本模块判定：
  ```c
  values[17] = (frame[SBUS_FLAGS_BYTE] & (1 << SBUS_FAILSAFE_BIT)) ? 800 : 1400;
  ```

**接收机设置（用户确认）：**
- 失控时持续输出 SBUS 帧（接收机默认）；
- 开关通道的失控值为保持；
- CH7 是按钮；
- 横滚、俯仰、偏航、油门四个摇杆通道失控时回中，目前失控时的飞行表现是悬停。

对照 PX4 `v1.15.4` 标签的源码，得到以下推论。参数值均为 v1.15.4 默认值，机载以实际为准（第 14.4 节核对）。

| 编号 | 事实 | 依据（PX4 v1.15.4） | 对本方案的影响 |
| --- | --- | --- | --- |
| F1 | 原生解码中，CH17、CH18 是 SBUS 数字通道，只会是 998 或 1998。改动后的固件把 CH18 改写为失控标志：正常帧 1400，失控帧 800。CH18 是离散值，阈值 900 与两侧的距离为 100 和 500 | `src/lib/rc/sbus.cpp`（`sbus_decode` 数字通道解码） | 增加值域检查；出现 998 或 1998 说明飞控刷的可能是原生固件（第 5.1 节） |
| F2 | CH18 = 800 与其余通道来自同一个 SBUS 帧。经 `input_rc` → MAVLink `RC_CHANNELS` → `/mavros/rc/in` 后仍在同一条消息里，`RC_CHANNELS` 直接取 `input_rc` 的原始值 | `src/modules/mavlink/streams/RC_CHANNELS.hpp` | 可以逐帧门控：CH18 低的那一帧里，其余通道都是接收机的失控输出，不是飞手输入 |
| F3 | `rc_failsafe` 恒为 false，`rc_update` 把失控帧当作有效遥控输入：摇杆值照常进入 `manual_control_setpoint`，开关值照常进入 `manual_control_switches` | `src/modules/rc_update/rc_update.cpp`（`signal_lost` 判定） | 见 F4–F7 |
| F4 | 手动模式（POSCTL、ALTCTL、STABILIZED）在失控期间按接收机失控输出飞行，即失控预设值或保持的最后值。油门失控值低于中位时，POSCTL 会持续下降直到落地 | 同上 | 摇杆失控值回中（用户确认），所以失控时 POSCTL 是悬停。悬停不会返航，本模块仍需重新取得 OFFBOARD（D2） |
| F5 | 开关通道按变化动作：模式开关、解锁/急停开关、返航/悬停/OFFBOARD 开关的值一旦变化，飞控立即执行。失控输出如果改变了这些通道的值，失控瞬间和恢复瞬间各执行一次 | `src/modules/manual_control/ManualControl.cpp`（`processSwitches`） | 开关通道失控值为保持（用户确认），失控瞬间不会变化。恢复瞬间，如果飞手在失控期间拨过开关，飞控会在恢复时执行；模式变化由 reclaim 处理（D2、第 16 节） |
| F6 | 摇杆超控：`COM_RC_OVERRIDE` 第 0 位（默认开）使自动模式（含 AUTO.LAND）在摇杆变化超过 `COM_RC_STICK_OV`（默认 30%）时切到 POSCTL。实时值与失控值之间的跳变也算摇杆变化。第 1 位默认关，OFFBOARD 不受影响 | `src/modules/commander/Commander.cpp`（"Pilot took over using sticks"）、`ManualControl.cpp`（`sticks_moving`） | 链路丢失期间，AUTO.LAND 可能被切到 POSCTL 并一直悬停，降落中断（第 7.6 节） |
| F7 | OFFBOARD 丢失（setpoint 中断超过 `COM_OF_LOSS_T`，默认 1.0 s）后按 `COM_OBL_RC_ACT` 处理，默认 0 = 位置模式。遥控在飞控看来始终可用，所以会切到 POSCTL。这是模式回退，不改变用户意图，setpoint 恢复后 PX4 自动回到 OFFBOARD（`failsafe.cpp` 的 `checkModeFallback`；见系统性分析 N1） | `src/modules/commander/commander_params.c` | 用户决定保持 POSCTL（D10）。同步规划阻塞（B2）或节点异常时，飞机进入 POSCTL；链路丢失时摇杆失控值回中，所以是悬停。本模块把自身断流引起的回退与外部切出区分开（D22） |

| F9 | SBUS 没有 RSSI 来源时，`RC_CHANNELS` 的 rssi 恒为 255（未知），`/mavros/rc/in` 的 rssi 不能当作链路质量 | `RCInput.cpp`（`fill_rc_in`） | 维持 D6：只有 CH18 |

**系统层面的结论：** 原生失控保护被屏蔽后，失控处理完全依赖"本模块 + 接收机失控输出"。
- 本模块不在运行时（未启动、崩溃、MAVROS 中断），OFFBOARD 丢失后飞控切到 POSCTL（D10），之后按摇杆通道的失控值飞行（F4、F7）。
- POSCTL 中，横滚、俯仰杆控制水平移动，回中时刹停定点；油门杆控制升降，中位定高。四个摇杆失控时回中（用户确认），所以失控时 POSCTL 就是悬停。
- 这一前提由接收机设置保证，本模块不读取这些通道。更换接收机或改设置后，按第 14.4 节重新检查。

**对实飞现象的说明（原因待实飞复现）：**
- 摇杆失控值回中，失控时 POSCTL 是悬停。所以 dev 的"暂停"路径（A3、A5）表现为原地悬停、不再返航，而不是降落。
- 开关通道失控值为保持、CH7 是按钮，失控帧中的 CH7 是失控瞬间的值，通常是松开，"失控输出让 CH7 跳变、触发暂停"的可能性也不大。

能导致"原地降落"、需要排除的路径：

| 路径 | 条件 | 日志特征 |
| --- | --- | --- |
| 点数不足 | 触发时，或暂停中恢复时，录制点数少于 30，直接请求 AUTO.LAND（`backtrack_usecase.cpp:357-375`、`:308-354`） | 节点日志 "triggering AUTO.LAND"；状态进入 `LandingTransition` |
| 规划失败 | 判定"点过近"，或航点降级也构建失败（`backtrack_usecase.cpp:409-427`） | 节点日志 "too-close geometry" 或 "waypoint fallback construction also failed" |
| 其他节点请求 AUTO.LAND | 航线模块（px4_mimic_recorder dev）回放结束时，每 1 s 请求一次 AUTO.LAND（`src/core/fsm_controller.cpp` 的 `updateLandingRequest`）。实飞时航线模块在运行就需要排除 | 航线节点日志 "Mission finished, requesting AUTO.LAND" |
| 飞控自身的其他保护 | 例如数传与遥控共用一条无线链路时的数据链丢失保护（`NAV_DLL_ACT`），或电池保护 | PX4 日志中有 failsafe 事件；模式切换不是任何节点请求的 |

复现方法见第 14.5 节 FT0。原因如果在本模块之外（其他节点或飞控保护），本次重构解决不了，需要单独处理。

## 2. 目标与范围

### 2.1 目标

- G1：单一返航逻辑。返航开始后，其他触发只记录和上报，不打断（D3，第 6.4 节；验证 S1、S10）。
- G2：可预测的退出。只有明确、可靠的飞手指令能结束返航（D1、D20、D25，第 5.2、7.2 节；验证 S2、S3、S5–S8、S27）。
- G3：失控可靠。链路丢失期间保证处于返航；退出后失控时，沿新轨迹返航（D2、D7、D22，第 7.3、7.4 节；验证 S11、S12、S26，闭环场景 H03、H08）。
- G4：所有等待都有上限（时间或电量），超时后有确定的升级动作（D5、D11、D32，第 8 节；验证 S12、S17）。
- G5：结构上，条件每周期全量评估，转移只在状态机内，输出逐周期计算，支持表驱动测试（D26，第 4.2、6 节；验证 R2 的穷举检查）。
- G6：可调试：可开启调试日志，记录状态转换的原因、飞控模式变化和模式请求结果；需要时逐拍记录，能离线回放复现决策（D29，第 9.2 节；验证 S29–S31）。

### 2.2 不在本轮范围

- 不修改 `trajectory_core` 算法；不做轨迹环路裁剪。
- 不解决航线模块与返航模块同时发 setpoint 的仲裁问题（风险仍在，见第 16 节）。

## 4. 总体设计

### 4.1 分层与数据流

```mermaid
flowchart LR
  RC["/mavros/rc/in"] --> LM[LinkMonitor]
  RC --> PI[PilotInput]
  BAT["/mavros/battery"] --> BM[BatteryMonitor]
  ST["/mavros/state"] --> FC[飞控状态]
  EXT["/mavros/extended_state"] --> AM[在空中判定]
  ODOM["/Odometry_px4"] --> EXE[执行层：录制、轨迹/航点会话、游标]
  ODOM --> AM
  AM --> C
  LM --> C[Conditions 快照]
  PI --> C
  BM --> C
  FC --> C
  EXE --> C
  C --> SM["ReturnStateMachine::step"]
  SM --> O[输出：setpoint 策略、模式意图、执行命令、上报]
  O --> EXE
  O --> MC[ModeCommander：节流、观察结果、异步调用]
  MC --> SETMODE["/mavros/set_mode"]
  ST --> MC
  MC --> C
  O --> PUB[setpoint / 状态话题]
  EXE <--> PW[后台规划线程]
  SM -- 事件 --> LOG[DebugLog：events / trace]
  MC -- 事件 --> LOG
  PW -- 事件 --> LOG
```

### 4.2 设计原则

- P1：检测与决策分离。条件层只输出电平值，以及带编号的按键指令，自己不做取舍；状态机决定是否响应，不会丢弃条件。
- P2：单一转移入口。所有转移都在 `step(conditions)` 中完成，UseCase 不直接改状态。
- P3：输出逐周期计算。setpoint 策略和模式意图由当前状态和条件算出；拿不到目标时保持当前位置，绝不输出原点。
- P4：安全不对称。让飞机更安全的指令（主动返航）在信号退化时照常接受；降低安全的指令（退出、外部切出）只在链路正常时接受。
- P5：控制线程不阻塞：规划放在后台线程，模式服务调用异步执行（D24）。
- P6：一切等待都有上限（时间或电量）。不了解下方环境时，悬停优先于降落（D10、第 8 节）。
- P7：控制权显式化。是否发布 setpoint、是否请求模式，取决于区域 B 的控制权状态；模式变化要区分来源：飞手、飞控回退、本模块自身（D22、D25、D26）。

## 5. 条件层

条件层的组件只做检测，每周期输出一份 `Conditions` 快照，不包含任何状态转移。

### 5.1 LinkMonitor（链路）

输入：每帧 RC 消息的 CH18 值和接收时间。CH18 与其余通道同帧到达（F2），逐帧判定。

| 输出 | 判定 |
| --- | --- |
| `ch18_low_now` | 当前帧 CH18 < `ch18_failsafe_threshold`（900） |
| 值域检查 | 正常帧 CH18 应为 1400，失控帧为 800（F1）。出现其他值时告警 `CH18_UNEXPECTED`，仍按阈值判定。998 或 1998 是原生解码的值，说明飞控刷的可能是原生固件：模块的失控检测失效，由 PX4 原生保护处理 |
| 漏桶 `loss_bucket_s` | CH18 低时每秒加 1，正常时每秒减 `link_loss_leak_rate`（0.2），最小为 0，最大为 `ch18_confirm_s`（R-55）。按帧间保持上一帧的值积分，结果与 tick 相位无关 |
| `link_lost`（来源 ch18） | `loss_bucket_s` ≥ `ch18_confirm_s`（1.0）。连续掉线 1 s 时，结果和现有判定完全一致 |
| `link_lost`（来源 rc_timeout） | 沿用 `rc_loss_timeout_s` + `rc_loss_debounce_s`：距最近一帧 ≥ 两者之和（0.25 s）即确认。RC 超时只在 tick 中判定；本模块自身卡顿（相邻两拍间隔 ≥ `rc_loss_timeout_s`）的那一拍不判定，因为卡顿期间到达的 RC 消息还在回调队列里（R-61） |
| `link_lost` 清除 | CH18 连续正常至少 `link_recover_s`（2.0），且 RC 消息正常。漏桶不清零，按泄漏率继续下降，所以恢复后短时间内再次掉线会更快确认：恢复 2 s 时漏桶至多 0.6，再掉线 0.4 s 即确认 |
| `link_degraded` | 最近 `link_degraded_window_s`（5.0）内出现过 CH18 低或 RC 消息超时（距上一帧 ≥ `rc_loss_timeout_s`，不去抖），或 `link_lost` 为真 |
| 通道检查 | 启用了 CH18，但还没有收到 RC 消息，或通道数少于 18 时，告警 `CH18_UNAVAILABLE`，不再静默视为正常（R-59）。此时 CH18 不参与判定：既不算失控帧，也不算退化，否则飞手拨开关会一直被当作链路异常而被 reclaim 覆盖 |

几个时序示例：
- 连续掉线：1.0 s 确认。
- 每秒掉 0.3 s：第 6 次掉线时确认（约 5.2 s）。
- 每 2 s 掉 0.1 s：不会确认，只报退化。

局限：CH18 只反映接收机宣布的失控。接收机宣布失控前有自己的保持时间，期间输出最后一帧的值。丢包时长不足以让接收机宣布失控时，模块看不到（见第 16 节）。

### 5.2 PilotInput（CH7）

- 每帧更新：`pressed = CH7 < ch7_pressed_threshold`。
- 链路门控（逐帧，依据 F2）：当前帧 `ch18_low_now` 为真，或 RC 超时（距上一帧 ≥ `rc_loss_timeout_s`）时，通道值是接收机失控输出或已经过时，视为不可信：不计时、不产生指令，当前按下作废。RC 超时后到达的第一帧与之前的帧不相连，不能构成按下沿。
- 按下沿：只有前一帧和当前帧都是正常帧、前一帧松开、当前帧按下，才算一次新按下：`press_id` 加 1，并记录按下开始时间。门控结束后，必须先在正常帧中看到松开，才接受下一次按下。这样：
  - 失控帧中 CH7 为"按下"时（例如失控瞬间飞手正按着，接收机保持了这个值），恢复瞬间跳回松开不会被当作一次短按；
  - 恢复时飞手正按着 CH7，这次按下也不算。
- 指令以 `press_id` 标识，同一次按下最多产生一条指令。指令带按下开始时间和链路标志 `link_ok`，保留到同类的下一条指令产生为止，所以落在两个 tick 之间的按键也不会丢。状态机按 `press_id` 消费，并记录已消费的编号（R-56）。
- 条件层只给出事实，是否响应由状态机决定（P1）：`link_ok` 为假时不响应；`exit_request` 的按下开始时间不晚于当前任务的开始时间时不响应；任务中收到 `link_ok` 为假的 `exit_request` 时告警 `EXIT_REJECTED_LINK`。
- 新的飞行周期开始时，作废进行中的按下（须先松开），清除未消费的指令。`press_id` 继续递增、不归零，避免新按键的编号小于状态机记录的已消费编号（R-57）。

| 指令 | 产生条件 | `link_ok` | 状态机另外要求 |
| --- | --- | --- | --- |
| `return_request` | 同一次按下持续达到 `ch7_hold_s`（2.0 s）时产生 | 此时链路未丢失（允许退化） | — |
| `exit_request` | 同一次按下持续 ≥ `ch7_exit_min_s`（0.3 s），并在 `ch7_hold_s` 之前松开（**短按，松开时产生**） | 按下全程链路正常，没有退化 | 按下开始时间晚于当前返航任务的开始时间 |

为什么退出要求"短按、松开时生效"：
- 返航中长按 CH7 不会误退出。飞手可能并不知道返航已经被其他条件触发，又按 CH7 想"触发返航"（对应现状问题 A4）。
- 紧急接管可以直接拨模式开关，链路正常时立即生效（第 7.2 节）。

### 5.3 BatteryMonitor（电量）

- 有效性：`percentage` 为 NaN、小于 0 或大于 1 时视为无效，不参与判定，并告警 `BATTERY_INVALID`。还没有收到读数时同样告警，起飞前检查才能发现电量话题缺失（R-59）。
- `battery_low`：有效读数持续低于 `low_battery_threshold` 达到 `low_battery_confirm_s` 后置位，锁存到本次飞行结束（新的飞行周期复位）。
- 读数无效期间，`battery_low` 保持原值。超时升级不把"无效"当作低电量（D11），相应风险见第 16 节。
- 无效读数既不打断也不推进确认（R-60）：确认计时从第一次有效的低读数开始，有效读数回到阈值以上才清零；只在最近一次读数有效时置位。
- 是电平语义，不存在"被消费"。

### 5.4 落地与在空中判定

新增订阅 `/mavros/extended_state`（`mavros_msgs/ExtendedState`）。

`airborne`（在空中）是正向判定，两个条件同时满足才为真（D23）：
- `landed_state ≠ ON_GROUND`；没有收到消息、状态未定义，或超过 `fcu_state_stale_s`（3 s）没有更新时，视为满足；
- 当前里程计高度比解锁高度 `z_arm` 高出 `airborne_min_height_m`（0.5 m）。`z_arm` 在每个飞行周期开始（观察到从未解锁到解锁）时取当时的里程计高度；那时还没有里程计时，与下面的空中重启一样只按 `landed_state` 判定（R-68）。

节点在飞机已解锁时启动（例如空中重启），没有观察到解锁过程，也就没有 `z_arm`：本次飞行只按 `landed_state` 判定。否则会把重启时的空中高度当作解锁高度，本次飞行再也无法启动返航（R-58）。判定解锁过程只用 `connected` 为真的 `/mavros/state`：MAVROS 未连上飞控时也发布 `armed=false`，会被误当成"未解锁"。同理，`landed_state` 过期视为未定义，避免 `/mavros/extended_state` 中断后停在 ON_GROUND，一直阻止返航。

不能只看 `landed_state` 的原因（系统性分析 N2）：PX4 判定落地需要"指令下降 + 低推力"。触地瞬间关遥控器时摇杆回中，OFFBOARD 原地保持时 setpoint 不带下降速度，这两种情况下 PX4 都不会报告落地，也不会自动上锁（仿真 H06a）。

落地保护有两层：
- `airborne` 为假时不启动任务（第 6.4 节）。
- 任务的悬停、准备阶段 `airborne` 变为假时，直接请求 AUTO.LAND，不起飞（第 6.3 节规则 3）。AUTO.LAND 会给出下降指令，飞控随后判定落地，并按 `COM_DISARM_LAND` 上锁。跟随、到点、交接阶段只看 `landed_state == ON_GROUND`，因为返航路径的末端本来就可能贴近起飞高度。

局限：降落在比起飞点高的平台上时，或者节点在空中重启后，高度条件不起作用，只能依赖 PX4 的判定；SLAM 的高度漂移需要在实飞中评估（第 16 节）。

### 5.5 输入新鲜度

| 条件 | 判定 |
| --- | --- |
| `odom_stale` | 距最近一次 odom 超过 `odom_stale_s`（0.25 s） |
| `fcu_state_stale` | 距最近一次 `/mavros/state` 超过 `fcu_state_stale_s`（3.0 s）；MAVROS 心跳为 1 Hz |

接收时间统一取回调时刻的 `ros::Time::now()`。dev 的 `onRCReceived` 已经是这样做的。里程计中断不单独判定（D31）：延迟时冻结进度、原地保持，一直持续到里程计恢复。

里程计的位置、速度或 yaw 含非有限值（NaN、Inf）时视为没有收到：不更新位置，也不更新接收时间，由上表的新鲜度判定接管，0.25 s 后保持在最后一个有效位置（R-73）。

### 5.6 执行事实

以下事实由执行层提供，作为条件的一部分。每拍先更新条件层，再用执行层最近一次的结果组装条件、调用 `step()`；`step()` 之后按本拍输出执行命令（规划、复位）、推进跟随进度、计算 setpoint 和偏离判定。所以偏离、到点等事实比位置晚一拍（50 ms），对持续判定没有影响（R-71）：

| 事实 | 含义 |
| --- | --- |
| `has_min_points` | 录制点数 ≥ `record_min_points` |
| `plan_status` | none / pending / ready / ready_fallback / failed_too_close / failed_fallback（配置启动时校验，没有 failed_config，R-88） |
| `planning_slow` | 规划中，且距提交已超过 `planning_warn_s`（10 s）（R-76） |
| `planning_timed_out` | 本任务的航点降级来自规划超时（第 7.5 节），持续到任务结束（R-76） |
| `path_start_yaw` / `path_target_yaw` | 轨迹就绪后的路径起始切向 / 跟随阶段当前路径目标的切向。是否对准（yaw 误差 ≤ 15°）由状态机用当前 yaw 计算：准备阶段对准起始切向，重新接入时对准目标切向；航点降级没有切向，不要求对准 |
| `remaining_m` | 剩余路径长度，用于停滞判定：轨迹为路径总长减投影弧长，航点降级为当前目标航点到终点的折线长度（R-85） |
| `deviation_confirmed` / `rejoin_confirmed` | 沿用现有的持续判定；局部投影失败也算偏离（与 dev 相同） |
| `finished` | 轨迹或航点降级会话完成 |
| `projection_ok`、`cross_track_m` | 当前位置在跟随进度附近的局部投影是否有效、横向偏差。每拍按当前位置计算，只查询、不推进进度，所以跟随进度冻结时（例如重新申请期间）仍反映当前偏差（R-74）。航点降级没有投影：按有效提供，偏差取到当前目标航点的距离（D30） |
| `trail_gap` | 规划用的轨迹在断点处截断，不通到录制起点（第 7.8 节） |
| `anchor_ahead` / `anchor_past_gap` | 找点接上（第 7.8 节）：游标之前 / 断点之前有离飞机不超过安全距离的录制点（R-83、R-84） |
| `stream_gap_recent` | 最近 `fallback_window_s`（3 s）内，本模块相邻两次发布 setpoint 的最大间隔 ≥ `fallback_gap_s`（0.5 s）。用于区分飞控回退和外部切出（D22）。只在连续发布期间计算：某一拍不发布即结束这一段，下次发布重新开始，所以新任务的第一次发布不算断流；卡顿结束后的第一拍，距上次发布的时间也算一次间隔（R-69） |
| `mode_request` | `ModeCommander` 提供：最近一次请求的模式、发出时间和结果（已生效 / 未生效 / 失败） |

## 6. 状态机

### 6.1 结构：三个并行区域

状态机按职责分成三个并行区域（D26）。每个区域只回答一个问题，各自的转移表都很小，可以分别穷举；组合行为只由下面几条耦合决定。

| 区域 | 状态 | 回答的问题 |
| --- | --- | --- |
| A 任务阶段 | 未解锁、录制前、录制、任务（悬停 → 准备 → 跟随 → 到点 → 交接）、已退出、飞控降落 | 现在要做什么 |
| B 控制权 | `none`、`acquiring`、`owned`、`fallback`、`reclaiming`、`handover`、`yielded`、`fcu_landing`（第 6.2 节） | 现在能不能做 |
| C 跟随方式 | 在路径上、回归路径 | 怎么跟踪路径；只在"跟随"阶段有效 |

区域之间的耦合：
1. 区域 B 不处于 `owned` 时，区域 C 冻结进度，停滞计时和准备计时也冻结（R-18）。
2. 区域 B 判定为飞手接管（第 6.3 节规则 4b、4c），或收到短按退出 → 区域 A 进入"已退出"，区域 B 进入 `yielded`。
3. 区域 B 的 `reclaiming` 超时 → 按第 8.1 节升级 → 区域 A 进入"交接"。
4. 区域 A 的悬停、准备阶段让区域 B 从 `none` 进入 `acquiring`；交接阶段让区域 B 进入 `handover`，把控制交给 AUTO.LAND。
5. 任务中判定落地（第 5.4 节）→ 区域 A 进入"交接"，直接请求 AUTO.LAND。

上报给前端的状态字符串由三个区域推导。现有字符串保持不变；删除 `Paused`，新增 `Exited`。

| 状态字符串 | 区域 A | 区域 B | 区域 C | 语义 |
| --- | --- | --- | --- | --- |
| `IdleDisarmed` | 未解锁 | `none` | — | 未解锁 |
| `WaitRecordDelay` | 录制前 | `none` | — | 解锁后的录制延时 |
| `Recording` | 录制 | `none` | — | 录制中 |
| `Ch18HoverWait` | 任务·悬停 | `acquiring` 或 `owned` | — | 失控触发后悬停 `ch18_hover_wait_s`（15 s）；后台规划同时进行 |
| `ReturnPreOffboard` | 任务·准备 | `acquiring` 或 `owned` | — | 等规划、进 OFFBOARD、起始对准；找点接上后也回到这里（第 7.8 节） |
| `ReturnActive` | 任务·跟随 | `owned` 等 | 在路径上 | 沿轨迹返航 |
| `ReturnRejoin` | 任务·跟随 | `owned` 等 | 回归路径 | 沿路径低速回归 |
| `LandingHover` | 任务·到点 | `owned` 等 | — | 到点悬停 |
| `LandingTransition` | 任务·交接 | `handover` | — | 降落交接 |
| `Exited` | 已退出 | `yielded` | — | 飞手退出后：不控制、继续录制、只告警；失控时启动新任务 |
| `AutoLandYield` | 飞控降落 | `fcu_landing` | — | 飞控降落已接管，锁存到上锁 |

"`owned` 等"指任务中区域 B 也可能处于 `fallback` 或 `reclaiming`。此时状态字符串不变，由上报字段 `control` 区分。

### 6.2 区域 B：控制权（上报字段 `control`）

| 值 | 含义 |
| --- | --- |
| `none` | 未参与控制 |
| `acquiring` | 正在申请 OFFBOARD，尚未确认 |
| `owned` | 本任务内已确认 OFFBOARD，且当前就是 OFFBOARD |
| `fallback` | 本模块刚断流，飞控回退到 POSCTL；继续发布，等飞控自动回到 OFFBOARD（D22） |
| `reclaiming` | 链路丢失或退化时被切出，正在重新申请（第 7.3 节） |
| `handover` | 降落交接中，正把控制交给 AUTO.LAND |
| `yielded` | 已退出，控制交还飞手 |
| `fcu_landing` | 飞控降落已接管（`AutoLandYield`） |

"OFFBOARD 已确认"是任务级标志：本任务内一旦观察到 `mode == OFFBOARD` 就置位，新任务开始时清零。

```mermaid
stateDiagram-v2
  [*] --> none
  none --> acquiring: 任务开始
  acquiring --> owned: 观察到 OFFBOARD
  acquiring --> yielded: 确认前飞手切到其他模式（链路正常）/ 短按退出
  owned --> fallback: 被切出，且本模块刚断流
  fallback --> owned: 飞控自动回到 OFFBOARD
  fallback --> yielded: 3 s 未回到，链路正常
  fallback --> reclaiming: 3 s 未回到，链路丢失或退化
  owned --> reclaiming: 被切出，链路丢失或退化
  reclaiming --> owned: 回到 OFFBOARD 并满足接入条件（第 7.3 节）
  owned --> yielded: 被切出，链路正常 / 短按退出
  owned --> handover: 进入降落交接
  handover --> fcu_landing: 飞控进入 AUTO.LAND
  yielded --> acquiring: 已退出后失控，开始新任务
```

图中省略了：任意值在上锁时回到 `none`；任意值在飞控进入 AUTO.LAND 时进入 `fcu_landing`；升级降落或任务中落地时进入 `handover`。

### 6.3 转移规则（每周期按优先级判定，命中后不再继续）

1. 未解锁：进入 `IdleDisarmed`。新的飞行周期（从未解锁到解锁）开始时，复位任务、轨迹、电量锁存和按键状态（第 5.2 节），并记录解锁高度 `z_arm`（第 5.4 节）。
2. 已解锁且 `mode == AUTO.LAND`：进入 `AutoLandYield`，锁存到上锁（与现在相同）。PX4 的 Descend 也上报为 AUTO.LAND。锁存期间链路丢失、模式离开 AUTO.LAND 时，重新请求 AUTO.LAND（第 7.6 节）。
3. 任务中落地（D23）：悬停或准备阶段 `airborne` 为假，或其他阶段 `landed_state == ON_GROUND`：进入 `LandingTransition`，直接请求 AUTO.LAND，告警 `MISSION_LANDED`（第 5.4 节）。
4. 任务中的模式变化（`/mavros/state` 新鲜时判定）：
   - a. 回退（D22）：OFFBOARD 已确认，当前模式不是 OFFBOARD，且 `stream_gap_recent` 为真（第 5.6 节）→ 区域 B 进入 `fallback`：保持任务、继续发布 setpoint、不申请模式，告警 `OFFBOARD_FALLBACK`。飞控在 setpoint 恢复后会自动回到 OFFBOARD（F7）。`fallback_timeout_s`（3 s）内仍未回到 OFFBOARD 时，按 b 处理。
   - b. 外部切出：OFFBOARD 已确认，当前模式不是 OFFBOARD，且不属于 a：
     - 链路正常（没有退化）：进入 `Exited`，原因 `EXTERNAL_MODE`；
     - 链路丢失或退化：进入 `reclaiming`（第 7.3 节）。
   - c. 确认前接管（D25）：OFFBOARD 尚未确认，链路正常（没有退化），当前模式既不是任务开始时的模式（第 7.1 节），也不是 OFFBOARD → 进入 `Exited`，原因 `EXTERNAL_MODE`。链路退化时不判为接管，继续申请 OFFBOARD（P4）。`/mavros/state` 约 1 Hz，为了先看到飞手的切换、再发出申请，链路正常时预发结束后，须等到下一条飞控状态，才申请 OFFBOARD（R-75）。
   - 例外：`LandingTransition` 中我方已经请求了 POSCTL 或 AUTO.LAND，所以 POSCTL 属于预期模式，不算切出。链路丢失或退化时，`LandingTransition` 中出现其他模式也不进入 `reclaiming`，而是继续请求 AUTO.LAND（第 7.6 节）。
   - 飞控状态中断（`fcu_state_stale`）时：规则 2 的进入判定和规则 4 全部暂停，各计时照常，恢复后按当时的数据判定；输出沿用最后一次收到的模式（R-62）。
5. 任务中收到 `exit_request`：进入 `Exited`，原因 `PILOT_EXIT`。
6. 超时升级（第 8.1 节）：在规则 7 之后判定。按本阶段的规则仍不能继续返航、某个等待已超时且确认低电量时，进入 `LandingTransition`，直接请求 AUTO.LAND（R-85）。
7. 执行当前状态自身的规则（见第 6.6 节状态图）。

- **同周期多个条件成立：** `Recording` 中同一周期有多个条件成立时，只启动一个任务。只要其中有失控，就走悬停路径。原因记录第一个成立的条件，其余写入任务的"已出现条件"。

### 6.5 每周期输出

状态机每周期输出 setpoint 和"模式意图"；何时真正发送模式请求，由 `ModeCommander` 决定（第 7.7 节）。

| 状态 / 区域 B | setpoint | 模式意图 |
| --- | --- | --- |
| Idle / WaitRecordDelay / Recording | 无 | 无 |
| `Ch18HoverWait` | 保持触发点 | 预发 `pre_offboard_setpoint_count`（6 帧，0.3 s）后为 OFFBOARD；链路正常时还要等到预发结束后的下一条飞控状态（R-75） |
| `ReturnPreOffboard` | 保持触发点（重新接入、找点接上后为当时的位置，第 7.8 节）；规划就绪后 yaw 改为路径起始切向 | OFFBOARD |
| `ReturnActive` | 轨迹目标；拿不到目标时保持当前位置 | OFFBOARD |
| `ReturnRejoin` | 限速后的轨迹目标；拿不到目标时保持当前位置 | OFFBOARD |
| `fallback`（区域 B） | 照常输出当前状态的 setpoint（跟随进度冻结） | 无，等飞控自动回到 OFFBOARD |
| `reclaiming`（区域 B） | 保持进入 `reclaiming` 时的位置；yaw 在跟随阶段为路径目标切向，其他阶段沿用原保持 yaw | OFFBOARD |
| `LandingHover` | 保持到点位置 | OFFBOARD |
| `LandingTransition` | 飞控离开 OFFBOARD 之前保持 | 链路正常：POSCTL → AUTO.LAND；链路丢失、升级降落或已落地：直接 AUTO.LAND |
| `Exited` | 飞控离开 OFFBOARD 之前保持当前位置 | 处于 OFFBOARD 且链路未丢失时为 POSCTL，之后无（链路丢失时只保持，由新任务接管，R-67） |
| `AutoLandYield` | 无 | 无；链路丢失且模式不是 AUTO.LAND 时为 AUTO.LAND |

`Ch18HoverWait` 和 `ReturnPreOffboard` 的输出由同一个函数计算：保持位置、预发 setpoint、申请 OFFBOARD。两者只差离开条件：前者是悬停时长到期，后者是规划就绪、进入 OFFBOARD 并完成对准。dev 中这两段重复的预发和切 OFFBOARD 逻辑（`state_machine.cpp:219-294`）由此合并（D16、R-37）。

预发帧数从 20 改为 6（D27）：PX4 进入 OFFBOARD 只要求最近 1 s 内有 setpoint（`offboardCheck.cpp`），0.3 s 的连续发布已经足够，失控后能更快进入 OFFBOARD。

是否录制：只在 `Recording` 和 `Exited` 中录制。

是否发布 setpoint：录制前和 `Recording` 中都不发布。`Recording` 中航线模块可能正在用 OFFBOARD 飞行，本模块在任务开始前发布 setpoint 会提前与航线模块冲突（R-33）。

## 7. 关键机制

### 7.1 返航任务（mission）

- 同一时刻最多一个任务。
- 任务开始时记录：
  - `id`：本次飞行内递增；
  - 原因：首个成立的条件；
  - 开始时刻的条件集合和开始时间；
  - 开始时的飞控模式，用于判断 OFFBOARD 确认前的飞手接管（第 6.3 节规则 4c）；
  - 轨迹快照：任务期间不录制，录制缓存就是快照。
- 任务期间新出现的条件，写入"已出现条件"并记录首次出现时间，同时上报，但不改变流程（D3）。
- 任务以 `AutoLandYield`、`Exited` 或上锁结束。在 `Exited` 中失控会开始新任务（`id + 1`）。

### 7.2 退出

**进入退出的三种情况（D1、D20）：**
- 收到 `exit_request`；
- 链路正常时被外部切出 OFFBOARD，不含本模块自身断流引起的回退（D22）；
- OFFBOARD 确认前，链路正常时飞手把模式切到 OFFBOARD 以外的模式（D25）。

**退出时的动作：**
1. 取消规划；
2. 截断轨迹（第 7.4 节）；
3. 恢复录制；
4. 飞控离开 OFFBOARD 之前，保持当前位置并请求 POSCTL。3 s 仍未生效就告警并继续请求，飞手也可以直接拨开关。

**退出后：** 低电量和 CH7 长按只告警；失控启动新任务。

### 7.3 链路丢失时重新申请控制权（reclaim）

- **进入条件：** 任务中，OFFBOARD 已确认，当前模式不是 OFFBOARD 也不是 AUTO.LAND，链路丢失或退化，并且不是本模块自身断流引起的回退（D22）。
- **期间动作：**
  - 保持当前位置：观察到 OFFBOARD 之前，保持点跟着飞机的当前位置；观察到之后固定在当时的位置，不飞回切出时的位置（D30）。模式意图为 OFFBOARD，由 `ModeCommander` 按间隔发送（第 7.7 节）；
  - yaw：任务处于 `ReturnActive` 或 `ReturnRejoin` 时设为路径目标切向，其他状态沿用该状态原本的保持 yaw；
  - 冻结返航进度、游标、停滞计时和准备计时，由 reclaim 自己的超时负责升级，避免重复升级；
  - 失控悬停的 15 s 照常计时。
- **结束条件：**
  - 所有状态都要求观察到 OFFBOARD。
  - 任务处于 `ReturnActive` 或 `ReturnRejoin` 时，还必须同时满足：
    1. yaw 误差 ≤ 15°；
    2. 局部投影有效，且横向偏差 ≤ `safe_distance_m`（0.7 m，D30）。

  满足后：横向偏差 ≤ `rejoin_trigger_dist_m` 时回到原状态；否则进入 `ReturnRejoin`，沿路径低速收敛。
- **其他阶段重新接入：** 悬停、准备、到点阶段重新接入后，保持点改为重新接入时的位置；之后开始跟随前同样检查偏差（第 7.8 节）。
- **投影失败或偏差超过安全距离：** 原地保持并告警 `PATH_OFFSET`，不直线拉回；能找点接上时重新接入，从接上的点重新规划（第 7.8 节）。否则继续保持，仍按重新申请的计时（从进入 reclaiming 算起）升级（第 8.1 节，R-85）。这一条处理的是 B3：飞机漂出投影窗口时，现有逻辑会朝旧目标直线移动。
- **超时：** 进入时即告警 `RECLAIMING`；10 s 仍未重新接入，告警 `RECLAIM_TIMEOUT`，按第 8.1 节升级。
- **链路先恢复：** 重新申请期间链路恢复正常（没有退化），而模式仍不是 OFFBOARD 时，按规则 4b 进入 `Exited`，飞手当时的模式选择生效（R-63）。
- **不与飞控降落争夺控制：** 对 AUTO.LAND（PX4 的 Descend 也上报为 AUTO.LAND）始终让步。

### 7.4 退出后沿新轨迹返航（D7）

**游标：** 用来定位返航已经走到哪个录制点，在执行层维护（R-77）。
- 任务开始时，`cursor` 指向轨迹末点，即触发点（任务期间不录制，录制缓存不变）。
- 找点接上时录制截断到接上的点，`cursor` 指向这个点，即截断后的末点（第 7.8 节）。
- `ReturnActive` 和 `ReturnRejoin` 中，跟随进度推进的那一拍（持有控制权、里程计新鲜）：从 `cursor` 往前 `cursor_window_m`（2.0 m）弧长范围内，找离"路径投影点"最近的录制点；航点降级时改用飞机位置。路径投影点是轨迹上投影弧长处的点。进度冻结时（R-18）游标也不动（R-77）。
- `cursor` 只减不增；距离相同时取更小的索引。
- 窗口按录制点之间的累计距离划分，所以悬停时堆积的密集点能一次跨过；只做局部搜索并且单调推进，路径自交时也不会误判。

**截断：**
- 退出时只保留 `[0, cursor]` 段，不按退出时的阶段区分（R-78）。
- 退出位置与 `p[cursor]` 之间由规划直接连接。退出前飞机一直在沿路径跟踪，这段连接通常很短；超过安全距离时成为轨迹断点，新任务不会跨过它（第 7.8 节、D30）。

**续录：**
- `Exited` 中继续录制。
- 时间戳平移接续：第一个新点 = 末点时间 + 1/`record_max_hz`。这样可以避免 `trajectory_core` 因大间隙报告时间回退。录制在任务期间暂停后恢复时都这样接续，不论退出时是否截断（R-77）。

**新任务：** `Exited` 中链路丢失时，走与 `Recording` 相同的启动检查：不在空中（`airborne` 为假，第 5.4 节）时不启动，点数不足先等待补点。检查通过后进入 `Ch18HoverWait`，后台规划"截断后的轨迹 + 手动段"，然后返航。

**不同阶段退出的效果（R-78）：**
- 游标只在跟随时推进。在悬停或准备阶段退出（飞机还没沿返航路径移动）时，游标仍在末点，等于不截断（R-65）。
- 到点后游标已在起点附近，在 `LandingHover` 或到点后的 `LandingTransition` 退出，等于截断到起点。
- 半路进入降落交接（任务中落地、点数不足、规划失败，以及第 8 节的升级降落）后退出，保留游标之前的原路，新任务不会从退出位置直线飞向起点。

**局限：** 不做环路裁剪。如果手动段绕回了起点附近，新任务仍会先沿手动段飞回截断点，再回起点。

### 7.5 后台规划

**依据：** 附录 A 的实测数据和问题 B2。

**设计：** 移植 fix 分支的 `PlanningWorker`：
- 单工作线程，最多一个待处理请求；
- 用代次号丢弃过期结果；
- 正在运行的求解无法强行终止，取消时只丢弃结果。

**流程：**
- 任务一开始就提交规划，所以失控悬停的 15 s 期间规划在同时进行；
- 控制线程持续发布保持点；
- UseCase 持有的 `TrajectorySession` 改为 `unique_ptr`，规划结果在控制线程里接收。

**结果的处理时机：** `Ch18HoverWait` 期间返回的规划结果先保存，悬停结束、进入 `ReturnPreOffboard` 后再处理，包括需要降落的失败结果。这样 15 s 悬停不会被提前结束（D3）。

**失败处理（保留 dev 策略）：**

| 规划结果 | 处理 |
| --- | --- |
| 点过近 | 原地降落；规划用的轨迹在断点处截断时原地悬停（第 7.8 节） |
| 配置非法 | 启动时校验，非法则节点退出；运行时不会出现（R-88） |
| 其他失败 | 航点降级，降级会话在后台线程构建 |
| 航点降级也构建失败 | 原地降落；规划用的轨迹在断点处截断时原地悬停（第 7.8 节） |

**规划超时：** 超过 `planning_timeout_s`（30 s）就丢弃结果，在控制线程直接构建航点降级。这一步是 O(n)，很快，同一拍内得到 ready_fallback 或 failed_fallback。规划中超过 `planning_warn_s`（10 s）告警 `PLANNING_SLOW`；超时后告警 `PLANNING_TIMEOUT_FALLBACK`，持续到任务结束（R-76）。

**其他：**
- 规划 CSV 和 RViz 导出也移到后台线程。CSV 改写到调试日志的运行目录（第 9.2 节）放到 R7，与调试日志的其余部分一起做（R-76）。
- 上一个任务的求解还在运行时开始新任务（例如退出后马上失控），新请求排队，等旧求解结束后执行；新任务的规划超时从它自己的提交算起。节点退出时也要等正在运行的求解结束（R-76）。
- 单测让 `PlanningWorker` 不启动线程，在需要的时刻调用 `runPending()` 执行待处理的请求，结果到达的时刻由用例决定（与调试日志的 `flush()` 相同）；闭环场景使用真实线程，规划进行期间按墙钟推进仿真时间，结果到达的时刻与实际耗时一致（R-76）。

### 7.6 降落交接

- **链路正常：** 沿用 OFFBOARD → POSCTL → AUTO.LAND，以规避直接切 AUTO.LAND 时的航向突变。POSCTL 3 s 未生效则直接请求 AUTO.LAND。
- **链路丢失、升级降落或已落地：** 直接请求 AUTO.LAND。链路丢失时不经过 POSCTL，不依赖接收机的失控设置（F4）。
- **飞手接管：** 只在链路正常（没有退化）时判定。交接期间收到 `exit_request`，或模式变成 OFFBOARD、POSCTL、AUTO.LAND 以外的其他模式，视为飞手接管，进入 `Exited`。这一条处理问题 B4。链路丢失或退化时出现其他模式，不视为飞手接管，继续请求 AUTO.LAND。
- **AUTO.LAND 迟迟不生效：** 5 s 告警，持续请求。
- **AUTO.LAND 被切走（`AutoLandYield` 中）：**
  - 链路丢失期间，AUTO.LAND 可能被摇杆超控（F6）或恢复瞬间的模式通道变化（F5）切到 POSCTL。摇杆失控回中，飞机会一直悬停，降落中断。
  - 处理：`AutoLandYield` 中只要链路丢失、模式不是 AUTO.LAND，模式意图就是 AUTO.LAND，由 `ModeCommander` 按间隔（1 s）发送，并告警 `AUTOLAND_OVERRIDDEN`。不发 setpoint，不重启返航（锁存语义不变，D18）。
  - 链路正常时维持现有语义：飞手从 AUTO.LAND 接管后，模块不再干预。
  - 判定用的是"链路丢失"，不含退化：失控瞬间的跳变发生在确认之前，但确认后按电平补发请求；短暂掉线（不足以确认）时，飞手很快恢复控制，模块不干预。

### 7.7 模式请求（ModeCommander）

所有 `set_mode` 都由 `ModeCommander` 发出，状态机只输出"模式意图"（D24）。依据是系统性分析 N3：dev 中所有模式请求共用一个 1 s 节流，被节流时状态机并不知道；`set_mode` 返回成功只表示"已发出"；服务在 20 Hz 控制回调里同步调用。

- **发送：** 意图改变时立即发送；意图不变时按 `mode_request_interval_s`（1.0 s）重发，直到观察到目标模式。
- **异步：** 服务调用放在单独线程，不阻塞控制回调。
- **观察：** 在 `/mavros/state` 中看到目标模式即为生效。`mode_request_timeout_s`（3.0 s，至少容忍一次心跳丢失，R-14）内没看到，告警 `MODE_REQUEST_FAILED`，并作为条件提供给状态机。超时从当前意图第一次发出算起，意图改变时重新计时；告警持续到观察到目标模式、意图改变或意图消失。意图为"无"时不发送（R-70）。
- **失败：** `mode_sent=false` 或服务不可用时立即告警，同样按间隔重试。
- **上报：** 最近一次请求的模式、发出时间和结果。

### 7.8 安全距离（D30）

本模块只沿录制轨迹飞行。不在录制轨迹上的直线移动不超过安全距离 `safe_distance_m`（0.7 m）；超过时原地保持并告警，不直线飞过去（悬停优先，D10、D11；之后的升级见第 8 节）。

- **保持点取飞机所在的位置：** 任务开始时取触发点，到点时取到点位置，退出、交接、里程计延迟时取当时的位置；重新申请控制权期间跟着飞机的当前位置，重新拿到 OFFBOARD 后固定（第 7.3 节）；悬停、准备、到点阶段重新接入后，保持点改为重新接入时的位置。
- **开始和恢复跟随前检查偏差：** 从准备进入跟随、重新接入时，要求局部投影有效且横向偏差不超过安全距离。航点降级没有投影，偏差取到当前目标航点的距离。不满足时原地保持并告警 `PATH_OFFSET`。
- **跟随中偏离超过安全距离：** 局部投影失败或横向偏差超过安全距离时，不回归，原地保持并告警 `PATH_OFFSET`，冻结跟随进度；偏差回到安全距离以内后继续。回归只处理 0.5 m 到安全距离之间的偏离。
- **轨迹断点：** 录制轨迹中相邻两点相距超过安全距离（定位突跳、里程计中断、退出前飞机被移开）即为断点。规划只用末点到最近断点之间的连续段；返航到断点处原地悬停并告警 `TRAIL_GAP`，不降落。连续段太短、点过近或航点降级也构建失败时，同样原地悬停；第 7.5 节"原地降落"的几种失败只适用于没有断点的轨迹，因为那时飞机离录制起点不远。
- 无人机速度不超过 2 m/s，按 15 Hz 录制时相邻两点不超过 0.14 m，正常录制不会形成断点；里程计中断不在处理范围内（D31）。
- **找点接上（D33）：** 上面两种原地悬停（离路径超过安全距离、停在断点处），一开始就在录制轨迹中找离飞机不超过安全距离的点；找不到时每拍重新找，飞机或定位变化后可能找到：
  - 候选点：离路径超过安全距离时，为游标之前（还没返回经过）的点；停在断点处时，为断点之前的点。取候选点中离飞机最近的一个，直线移动最短；离路径超过安全距离时，断点之前也有候选点的话，优先接断点之前的，能越过断点（R-84）。
  - 找到：录制截断到该点（之后的点已返回经过、被跳过，或在断点之后用不上），从该点重新规划，回到准备阶段：原地保持，规划就绪后同样检查偏差、对准后跟随。飞机到该点的直线距离不超过安全距离，符合 D30。
  - 找不到：继续原地悬停并告警；确认低电量时原地降落（D32，R6）。
  - 要求持有控制权、里程计新鲜。重新申请控制权时拿回了 OFFBOARD、但偏差超过安全距离，同样找点接上，找到即重新接入。
  - 接上的点在游标之前；接上后游标就是这个点，下次只能接更早的点，所以不会在同一位置来回重规划。接上的点离飞机最近，准备阶段的偏差检查有余量。

## 8. 超时与升级

**原则：** 超时升级由本方案定义（D5）；不了解下方环境时，悬停优先于降落（D10、D11）。升级阶梯是：**告警 → 降级（换更简单的方法） → 保持等待 → 原地降落**。

### 8.1 返航无法继续

| 等待点 | 起算时刻 | 告警 | 超时 | 超时后：电量正常或读数无效 | 超时后：低电量 | 参数 |
| --- | --- | --- | --- | --- | --- | --- |
| 后台规划 | 提交规划 | 10 s | 30 s | 改为航点降级 | 同左 | `planning_warn_s` / `planning_timeout_s` |
| 准备：OFFBOARD + 起始对准 | 准备阶段中规划结果已出（就绪、航点降级或失败）；只在申请或持有 OFFBOARD 时累计 | 10 s：`PREPARE_SLOW` | 30 s：`PREPARE_TIMEOUT` | 保持并告警，继续尝试 | 不再要求起始对准，能开始跟随就开始；仍不能开始才原地降落（D32） | `prepare_warn_s` / `prepare_timeout_s` |
| 重新申请控制权（只在链路丢失或退化时出现；含拿回 OFFBOARD 后偏差超限的保持） | 进入 reclaiming | 进入时 `RECLAIMING` | 10 s：`RECLAIM_TIMEOUT` | 保持并告警，继续申请 | 原地降落（拿回 OFFBOARD 时已经找过点，第 7.3 节） | `reclaim_timeout_s` |
| 返航进度停滞（跟随阶段，以及停在断点处的到点悬停） | 剩余路径最近一次缩短 ≥ `stall_min_progress_m`（0.2 m）；只在持有控制权时累计 | 20 s：`PROGRESS_STALL` | 60 s | 保持并告警 | 原地降落（离路径超过安全距离、停在断点处时一直在找点接上，D33） | `stall_warn_s` / `stall_timeout_s` |

规则：
- "保持并告警"期间，链路正常时由飞手决定是否退出；链路丢失时等待链路恢复。
- 保持期间确认低电量时优先返航，只有返航也无法触发时才原地降落（D32）；原地降落较危险，是最后的选择。飞手已退出或接管（`Exited`）时不适用，低电量只告警（D1）。第 7.8 节的原地悬停（离路径超过安全距离、停在轨迹断点处）同样适用："能否返航"按找点接上判定（D33），悬停期间一直在找，确认低电量时仍找不到才原地降落。"优先返航"不能直线飞过超过安全距离的空间（D30）。
- 升级判定（规则 6）放在本阶段的规则（规则 7）之后：先按本阶段的规则继续返航，包括找点接上和低电量时不再等对准；仍不能继续、某个等待已超时且确认低电量，才原地降落（R-85）。
- 计时：各计时只在里程计新鲜时累计，里程计中断不会引起降落（D31）；重新申请期间，准备和停滞计时冻结，由重新申请的计时负责（R-18）。任务开始和找点接上时准备计时归零，进入跟随时停滞计时归零。
- 升级降落的交接原因为 `ESCALATED`，直接请求 AUTO.LAND，告警 `ESCALATED_LAND`。
- 电量读数无效时同样保持（D11）。这时电池耗尽前没有降落兜底，所以起飞前要确认电量读数有效（第 14.4 节、第 16 节）。
- 与上一版相比的变化（R-29）：链路丢失但电量正常或读数无效时，超时后不再原地降落，改为保持等待。里程计中断的处理已按 D31 取消。
- 靠近起点的降落保留 dev 策略：点数不足、"点过近"、航点降级也构建失败（第 6.4、7.5 节）。规划用的轨迹在断点处截断时，飞机不一定靠近起点，这两种规划失败改为原地悬停（第 7.8 节）。

### 8.2 交接与输入中断

| 等待点 | 起算时刻 | 告警 | 链路丢失时 | 链路正常时 | 参数 |
| --- | --- | --- | --- | --- | --- |
| 里程计延迟 | 最近一次 odom | 0.25 s：告警，同时冻结进度并保持，直到里程计恢复；中断不另作处理（D31） | 同左 | 同左 | `odom_stale_s` |

| 退出时 POSCTL 生效 | 请求 POSCTL | 3 s：`MODE_REQUEST_FAILED`（R-85） | — | 持续请求，飞手可直接拨开关 | 模式请求的参数 |
| 飞控状态中断 | 最近一次 `/mavros/state` | 3 s | 冻结所有依赖模式的判定 | 同左 | `fcu_state_stale_s` |
| 飞控回退后等待自动恢复 | 进入 `fallback` | 进入时告警 | 3 s 未回到 OFFBOARD：重新申请 | 3 s 未回到 OFFBOARD：退出 | `fallback_timeout_s` |
| 模式请求未生效 | 发出请求 | 3 s：告警 `MODE_REQUEST_FAILED` | 按间隔重发 | 同左 | `mode_request_timeout_s` / `mode_request_interval_s` |

"原地降落"指：从当前模式直接请求 AUTO.LAND，飞控离开 OFFBOARD 之前继续发保持点；飞控进入 AUTO.LAND 后，走现有的 `AutoLandYield`。链路丢失期间 AUTO.LAND 被切走时，按第 7.6 节重新请求。

## 9. 状态上报与告警

### 9.1 状态话题与告警

| 话题 | 类型 | 变化 |
| --- | --- | --- |
| `/px4_backtrack/state` | `std_msgs/String` | 新增 `Exited`，删除 `Paused` |
| `/status_rc_loss` | `std_msgs/Bool` | 含义改为"链路丢失"：CH18 累计确认或 RC 超时 |
| `/px4_backtrack/low_battery` | `std_msgs/Bool` | 不变，锁存到新的飞行周期 |
| `/px4_backtrack/status`（新增） | `std_msgs/String`（JSON） | 20 Hz 发布，内容见下例 |

```json
{"t": 1236.05, "flight": 1, "state": "ReturnActive", "control": "owned",
 "mission": 1, "reason": "LOW_BATTERY", "mode_request": "OFFBOARD", "mode_result": "applied",
 "alerts": ["LINK_LOST", "LOW_BATTERY"]}
```

`mission` 是本次飞行最近一次任务的编号，没有任务时为 0；`reason` 是它的原因（`PILOT_REQUEST` / `LOW_BATTERY` / `LINK_LOST`，与事件一致），没有任务时为 `NONE`。`mode_request` 是当前的模式意图（没有为空串），`mode_result` 为 `none` / `pending` / `applied` / `failed`。链路、电量、里程计和飞控状态的异常都有告警码，不再单独上报；任务中新出现的条件、事件记在调试日志里（R-88）。

告警码：

| 告警码 | 含义 |
| --- | --- |
| `LINK_LOST` / `LINK_DEGRADED` / `CH18_UNAVAILABLE` / `CH18_UNEXPECTED` | 链路丢失 / 链路退化 / CH18 通道不可用 / CH18 出现 800、1400 以外的值（998、1998 说明可能是原生固件） |
| `LOW_BATTERY` / `BATTERY_INVALID` | 低电量 / 电量值无效 |
| `RETURN_PENDING` | 已触发，等待补足录制点 |
| `TRIGGER_IGNORED_LANDED` | 不在空中（`airborne` 为假），触发被忽略 |
| `MISSION_LANDED` | 任务中判定落地，改为直接降落 |
| `EXIT_REJECTED_LINK` | 链路异常，拒绝退出；持续到链路恢复正常或任务结束（R-66） |
| `RETURN_EXITED` | 已退出返航 |
| `RETURN_REQUEST_IGNORED` | 退出后长按 CH7 不再启动返航（D1），按住期间告警（R-64） |
| `RECLAIMING` / `RECLAIM_TIMEOUT` | 正在重新申请 / 重新申请超时 |
| `PATH_OFFSET` / `TRAIL_GAP` | 离路径超过安全距离，原地保持 / 返航停在轨迹断点处悬停，不降落（D30） |
| `OFFBOARD_FALLBACK` | 本模块断流，飞控回退到 POSCTL，正在等待自动恢复 |
| `MODE_REQUEST_FAILED` | 模式请求超时未生效、被拒或服务不可用 |
| `DEBUG_LOG_FAILED` | 调试日志写入失败，已停止写日志（返航不受影响） |
| `PLANNING_SLOW` / `PLANNING_TIMEOUT_FALLBACK` | 规划慢 / 规划超时已改为航点降级 |
| `PREPARE_SLOW` / `PREPARE_TIMEOUT` | 准备慢 / 准备超时 |
| `PROGRESS_STALL` | 返航进度停滞（含停在断点处的到点悬停） |
| `ODOM_STALE` | 里程计延迟（D31 起不再区分中断） |
| `HANDOVER_DIRECT_LAND` / `AUTOLAND_OVERRIDDEN` | 交接改为直接降落 / 链路丢失期间 AUTO.LAND 被切走，正在重新请求。AUTO.LAND 未生效由 `MODE_REQUEST_FAILED` 表示（R-85） |
| `ESCALATED_LAND` | 已升级为原地降落 |
| `FCU_STATE_STALE` | 飞控状态中断 |

### 9.2 调试日志（D29）

**需求：** 提供可开启的调试日志，路径可配置，用于调试返航模块。要记录：
- 状态机三个区域的每次转换，带触发规则和原因；
- 飞控飞行模式和解锁状态的每次变化；
- 模式请求及其结果；
- 条件变化、任务开始与结束、规划结果、告警。

dev 目前只有零散的 rosout 文本（状态转换只记 from → to，不记原因；飞控模式变化不记）和规划时导出的 CSV，事后无法还原"为什么在这一刻做了这个动作"。

**设计：进程内的最小实现**
- **事件由核心产生。** `step()` 除了输出，还返回本拍发生的事件：区域转换、条件边沿、任务事件。所以事件内容可以单测。`ModeCommander`、规划线程和日志本身的事件，由外层补充。
- **写盘不进控制线程。** `DebugLog`（基础设施层）用一个后台线程写文件；控制线程只把一行文本放进有界队列。队列满时丢弃并计数，之后补写一条 `log_dropped` 事件。
- **每次节点启动建一个目录** `<debug_log_dir>/run_<YYYYmmdd_HHMMSS>/`，内含：
  - `events.jsonl`：一行一个事件；
  - `trace.csv`：仅在 `debug_log_trace` 为真时写，每拍一行：条件快照的全部字段，以及上报状态、控制权、模式意图、setpoint 种类、告警位、实际发布的 setpoint 和本拍耗时。枚举写数值，可选值缺失时留空，实数写 17 位有效数字，回放时与当时的数值完全一致；写和解析共用一份字段表。可以用 PlotJuggler 打开，也可以逐拍回放到 `step()`，复现当时的决策（R-88）；
  - `plan_<n>_input.csv`、`plan_<n>_trajectory.csv`：规划输入和结果，即原 `DebugDumper` 的 CSV，统一写到这里。`n` 是本次运行的第几次规划（找点接上后同一任务会再规划），提交规划的事件带 `plan=<n>`；输入每次都写，轨迹在就绪时写（R-88）。
- **第一条是 `config` 事件。** 内容是节点私有命名空间下的全部参数，以及本模块和 `trajectory_core` 的提交号（构建时写入，取不到时记为 unknown），便于复现（D13）。
- **只保留最近 `debug_log_keep_runs` 个运行目录**（含本次，按目录名排序），启动时删除更早的；本次的目录不删除。
- **写失败时**（磁盘满、无权限）停止写日志，告警 `DEBUG_LOG_FAILED`，返航不受影响。日志状态作为条件传给状态机，与其他告警一起计算和上报（R-72）。
- **关闭时**（`debug_log_enable: false`）不建目录、不写文件；状态话题和 rosout 照常。

**事件类型：**

| type | 内容 |
| --- | --- |
| `config` | 生效参数、版本 |
| `state` / `control` / `follow` | 区域 A / B / C 的转换：from、to、触发规则（第 6.3 节编号）、原因 |
| `fcu` | 飞控模式或解锁状态变化：from、to、armed |
| `mode_request` | 模式意图变化、请求发出、生效、失败 |
| `condition` | 条件边沿：链路丢失、退化、恢复（带来源），低电量，电量无效，`airborne` 变化，里程计延迟或中断，CH7 指令（含 `press_id`），CH18 异常值 |
| `mission` | 任务开始（原因、当时的条件集合）、任务中新出现的条件、任务结束（原因）、找点接上（原因 `PATH_OFFSET` / `TRAIL_GAP`）、录制截断（保留和删除的点数） |
| `planning` | 提交（点数）、完成（耗时、点数、结果）、失败、超时、改为航点降级、取消（任务结束时规划仍未完成） |
| `alert` | 告警出现和消失 |
| `stream` | 本模块断流（飞控回退是区域 B 的转换；每拍耗时在逐拍记录里，R-88） |
| `log_dropped` | 队列满时丢弃的行数 |

示例：

```json
{"t":1263.250,"flight":2,"mission":1,"type":"fcu","from":"OFFBOARD","to":"POSCTL","detail":"armed=true"}
{"t":1263.250,"flight":2,"mission":1,"type":"state","from":"ReturnActive","to":"Exited","rule":"4b","reason":"EXTERNAL_MODE"}
```

**查看：** 用 `jq` 过滤，或用 `scripts/analysis/show_debug_log.py` 按时间线打印（约 50 行，可按类型过滤）。

**可选：录原始话题。** 启动文件增加参数 `record_bag`（默认 false）。为真时，用标准 `rosbag record` 把以下话题录到启动参数 `bag_dir`（默认 `~/.ros`：rosbag 不建目录，要用一定存在的目录；运行目录由节点运行时建立，启动文件拿不到，R-88）：`/mavros/rc/in`、`/mavros/state`、`/mavros/extended_state`、`/mavros/battery`、里程计、`/mavros/setpoint_raw/local` 和本模块的话题。分片直接用 rosbag 自带参数，不写录制管理程序，也不计入保留的运行目录个数。

**不做：** 自定义 ROS 消息、独立的录制监控进程、离线检查报告工具。原因见附录 C。

## 11. 场景与期望行为

以下场景都写成 UseCase 级单测，规划器在单测中注入为同步实现。

| 编号 | 场景 | 期望行为 |
| --- | --- | --- |
| S1 | 低电量返航中失控，CH7 不变 | 继续返航；上报 `link_lost`，`control=owned` |
| S2 | 失控瞬间 CH7 出现单帧低值 | 不退出：链路门控，且单帧不满足短按条件 |
| S3 | 失控后 CH7 持续为低值，恢复瞬间跳回松开 | 不退出：链路丢失期间通道无效；恢复瞬间的松开不算一次短按 |
| S4 | 单独失控（`Recording` 中） | 从第一帧失控帧到进入 OFFBOARD ≤ 1.5 s（D27）；悬停 15 s 后返航；从 R4 起，规划在悬停期间后台进行 |
| S5 | 飞手按住 CH7 时低电量先触发 | 启动低电量任务；这次按下早于任务开始，不算退出；松开后重新短按才退出 |
| S6 | 返航中，链路正常时 CH7 短按 | 进入 `Exited`：截断轨迹，继续录制，请求 POSCTL |
| S7 | 返航中，链路正常时飞手拨模式开关 | 约 1 s 内感知，进入 `Exited` |
| S8 | 返航中长按 CH7 超过 2 s | 不退出、不暂停；记录 `return_request` |
| S9 | 录制延时内低电量 | 只告警；进入 `Recording` 并补足点数后返航 |
| S10 | `Recording` 中 CH18 与低电量同一周期确认 | 失控任务，悬停 15 s；低电量记入任务条件 |
| S11 | 退出后失控 | 新任务：悬停 15 s，沿截断轨迹 + 手动段返航，起点就是当前位置 |
| S12 | 链路丢失时被切出 OFFBOARD | 重新申请：偏移 ≤ 0.5 m 继续；0.5～0.7 m 进入 Rejoin；超过 0.7 m 或投影失败时保持并告警，10 s 后电量正常则继续保持，低电量则原地降落 |
| S13 | 落地未上锁时失控或低电量，包括触地瞬间关遥控器、飞控尚未报告落地的情形 | 不启动任务（高度差 < 0.5 m），告警 `TRIGGER_IGNORED_LANDED`（仿真 H06a、H06b） |
| S14 | 电量值为 -0.01 | 不判为低电量，告警 `BATTERY_INVALID` |
| S15 | 30 分钟录制后失控 | 悬停期间完成后台规划，控制循环不停发 setpoint |
| S16 | 规划超时 | 改为航点降级返航 |
| S17 | 链路丢失时返航进度停滞 60 s | 电量正常或读数无效：保持并告警，不降落；之后确认低电量时原地降落 |
| S18 | 降落交接中飞手拨开关 | 进入 `Exited`，不再请求 AUTO.LAND |
| S19 | 链路丢失期间 odom 中断 2 s | 已取消：里程计中断不处理（D31）；延迟期间冻结进度、原地保持 |
| S20 | 每秒掉 0.3 s 的间歇失控 | 第 6 次掉线时（约 5.2 s）确认失控并返航；之前只报退化 |
| S21 | 链路丢失期间，`AutoLandYield` 中模式被切到 POSCTL（摇杆超控） | 每 1 s 请求 AUTO.LAND，告警 `AUTOLAND_OVERRIDDEN`；链路恢复后停止请求 |
| S22 | CH18 出现 800、1400 以外的值（含原生固件的 998、1998） | 告警 `CH18_UNEXPECTED`，按阈值判定 |
| S23 | 降落交接中链路丢失，模式变为 ALTCTL | 不进入 `Exited`，继续请求 AUTO.LAND |
| S24 | `Recording` 中 CH18 低但未确认（漏桶未满） | 不发布任何 setpoint，不请求模式，只告警退化 |
| S25 | 失控在触地前一刻确认，任务开始后、悬停阶段高度差降到 0.5 m 以下 | 直接请求 AUTO.LAND，上锁，不起飞；告警 `MISSION_LANDED` |
| S26 | 返航中控制循环卡顿 1.3 s，飞控回退 POSCTL（链路正常） | 不退出；继续发布，飞控自动回到 OFFBOARD；告警 `OFFBOARD_FALLBACK`（D22，仿真 H13） |
| S27 | 返航开始、OFFBOARD 确认前飞手把开关拨到 ALTCTL（链路正常） | 进入 `Exited`，不再申请 OFFBOARD（D25，仿真 H14） |
| S28 | 飞控拒绝 OFFBOARD 请求 | 3 s 内告警 `MODE_REQUEST_FAILED`，按间隔重发（D24） |
| S29 | 打开调试日志，完成一次 S1（低电量返航中失控） | `events.jsonl` 按时间依次记录：低电量、任务开始（原因 low_battery）、控制权 acquiring→owned、飞控模式 POSCTL→OFFBOARD、链路丢失、到点、降落交接、飞控模式 OFFBOARD→AUTO.LAND（链路丢失时直接降落，第 7.6 节）、上锁；每条区域转换都带规则编号和原因 |
| S30 | 关闭调试日志 | 不建目录，不写文件 |
| S31 | 打开逐拍记录后回放 `trace.csv` | 逐拍重放 `step()`，输出与记录一致 |
| S32 | 链路退化期间飞手切出并把飞机飞开 20 m，随后链路丢失，模块重新拿到 OFFBOARD | 原地保持并告警 `PATH_OFFSET`，不飞回切出时的位置，也不直线飞回路径（D30） |
| S33 | 录制轨迹中有超过安全距离的跳变（定位突跳，或退出前飞机被移开） | 返航到跳变处原地悬停并告警 `TRAIL_GAP`，不跨过跳变，也不降落（D30） |
| S34 | 离路径超过安全距离或停在断点处，而录制轨迹的另一段（停在断点处时为断点之前的轨迹）离飞机不超过安全距离 | 从其中离飞机最近的点接上（断点之前有点时优先）：截断、重新规划，沿轨迹继续返航并在起点降落；找不到时原地悬停（D33） |

## 16. 残留风险与后续

| 风险 | 说明与建议 |
| --- | --- |
| 本模块不在运行时没有失控保护 | 原生保护已屏蔽。节点未启动、崩溃或 MAVROS 中断时，OFFBOARD 丢失后飞控切到 POSCTL（D10）；摇杆失控回中，所以是悬停。PX4 低电量动作只告警（D12），链路不恢复时，飞机会悬停到电池耗尽 |
| 电量读数无效时没有降落兜底（D11、D12） | 链路丢失、返航无法继续且电量读数无效时，本模块一直悬停，PX4 也不会因电量降落，电池耗尽前没有任何降落动作。缓解：起飞前确认没有 `BATTERY_INVALID` 告警（第 14.4 节） |
| 恢复瞬间执行失控期间拨过的开关（F5） | 开关通道失控值为保持，失控瞬间不会变化。但飞手在失控期间拨过的开关，会在链路恢复的瞬间执行：模式变化由 reclaim 处理，其他开关按飞手的意图执行 |
| SBUS 帧完全中断时原生保护介入（F8） | 接收机失控时持续输出帧，所以只剩硬件故障（断线、接收机掉电）。此时 PX4 先进入 Hold，再按 `NAV_RCL_ACT` 动作，与本模块的悬停、reclaim 同时发生；PX4 进入 AUTO.LAND 时模块让步。需在 SITL 中验证（第 14.3 节） |
| 部分丢包检测不到 | CH18 只反映接收机宣布的失控。改动后的 `sbus_decode` 已经能拿到 SBUS 的丢帧标志（frame lost 位）。建议后续把它也编码进一个通道，例如丢帧帧把 CH17 写为 800，由 `LinkMonitor` 统计丢帧比例判定退化。本轮不接入（D6、D19） |
| 退化窗口内飞手无法用开关接管 | 链路恢复后 `link_degraded_window_s`（5 s）内，飞手拨开关会被 reclaim 覆盖，需要在窗口结束后再拨一次。这是 P4 的代价 |
| 链路丢失期间地面站的模式指令也会被覆盖 | reclaim 和 `AutoLandYield` 的重新请求不区分指令来源（FT5 验证的就是这一行为） |
| 误刷原生固件 | CH18 变为 998 或 1998，模块不再感知失控，改由 PX4 原生保护处理。值域检查会告警 `CH18_UNEXPECTED`，起飞前就能在状态话题（第 9 节）中看到 |
| 在空中判定的局限（D23） | 降落在比起飞点高的平台上时，或节点在空中重启后（R-58），高度条件不起作用，只能依赖飞控的落地判定；SLAM 高度漂移可能让判定偏差，需要在实飞中评估 |
| 录制延时内失控不单独处理 | 解锁后 15 s 内飞机通常只离地约 1 m、离遥控器很近，失控概率小（2026-10-20 用户确认）。期间只告警，飞机按飞手当时的模式悬停（摇杆失控回中）；延时结束后链路仍丢失，按 `Recording` 中失控的规则启动任务（第 6.4 节） |
| 模块之外的断流无法识别为回退（D22） | 回退判定依据本模块自己的发布时间。如果断流发生在 MAVROS 或串口，本模块看不到，链路正常时会把飞控回退当作外部切出而退出返航；链路丢失时会重新申请，行为正确 |
| 调试日志可能丢失末尾内容 | 写盘在后台线程，控制线程只入队；节点崩溃时可能丢失最后约 0.2 s 的日志，队列满时会丢行（有计数） |
| 外部切出感知延迟约 1 s | 受 MAVROS 状态频率限制 |
| 不做环路裁剪 | 退出后手动段较长或绕回时，新返航路径较长。后续可按小半径做 SmartRTL 式环路裁剪 |
| 定位突跳不检测（D15） | 飞行中不检测。录制轨迹中超过安全距离的跳变成为断点，返航停在断点处悬停（D30）；跳变不超过安全距离时仍沿跳变段飞行。返航中定位突跳后，突跳后的位置若恰好离录制轨迹的另一段不超过安全距离，会从那里接上（D33） |
| `AutoLandYield` 仍然锁存 | 飞手从 AUTO.LAND 接管后，本次飞行不再受返航保护（维持现状，D18）。链路丢失时只会重新请求 AUTO.LAND（第 7.6 节） |
| 航线模块并发发布 setpoint | 本轮不处理，仍需要仲裁节点 |
| 失败分类依赖字符串（B6） | 建议后续由 `trajectory_core` 提供明确的错误码 |
| 机载规划耗时未知 | 需要在 RK3588 上实测（第 14.2 节） |

## 附录 A：轨迹生成耗时实测

方法：
- 复现命令：`scripts/docker/run_tests.sh amd64` 之后运行 `scripts/bench/run_gen_bench.sh amd64`（2026-10-19，本开发机 amd64，Docker ROS Noetic）。
- 调用 dev 的 `TrajectorySession::generate`，使用仓库当前的 `trajectory_config.yaml`。
- 输入为合成出航路径（`scripts/bench/gen_bench.cpp`，固定随机种子）：0.8 m/s，每 5 s 随机转向 ±69° 以内，约 1/6 的路段为悬停；里程计 30 Hz，经 `RecordingBuffer` 按 15 Hz 节流录制。
- 抽稀后点数取自生成时的日志。

| 录制时长 | 录制点数 | 抽稀后点数 | 生成耗时 |
| --- | --- | --- | --- |
| 1 min | 665 | 396 | 5 ms |
| 5 min | 3138 | 2377 | 149 ms |
| 10 min | 6313 | 4891 | 610 ms |
| 30 min | 19937 | 13010 | 4818 ms |

结论：
- 耗时随点数超线性增长，接近 O(n²)。2026-10-11 用临时程序测得的结果与此一致（10 分钟约 0.57 s，30 分钟约 4.9 s）。
- 与飞控的 OFFBOARD 丢失超时（`COM_OF_LOSS_T`，默认 1.0 s，以机载参数为准）相比：在 amd64 上，10 分钟录制约 0.61 s，已接近；30 分钟约 4.8 s，远超。
- RK3588 上的耗时需要实测（第 14.2 节）。

## 附录 C：`feat/return-diagnostics` 日志功能评估

该分支在 `fix/return-engineering-contracts`（`1152820`）之上，用 9 个提交（`3127b48`..`274fa42`）实现日志功能，共新增 3907 行：

| 类别 | 行数 | 内容 |
| --- | --- | --- |
| C++ 生产代码 | 674 | 每拍控制快照（70 多个字段）、规划证据、发布器、节点接线 |
| 自定义消息 | 103 | `ControlDiagnostics.msg`、`PlanningTrace.msg`，需要 message_generation |
| Python 工具 | 1088 | `record_flight_log.py`：独立进程，管理 rosbag 分片、磁盘空间、运行目录轮换；`inspect_flight_log.py`：离线检查报告 |
| 构建、配置、启动 | 81 | CMake、package.xml、8 个日志参数、启动文件增加录制节点 |
| 测试 | 1163 | C++ 单测、Python 单测、ROS 集成冒烟测试 |
| 文档与证据 | 798 | 使用说明、验证记录 |

| 维度 | 评估 |
| --- | --- |
| 与需求的匹配 | 能查到状态、模式和规划，覆盖了需求；但大部分代码花在需求之外：rosbag 的管理和离线报告 |
| 运行时复杂度 | 多一个 Python 进程和它管理的 rosbag 子进程；新增 4 个话题，其中控制快照 20 Hz，规划证据是包含全部原始录制点的大体积 latched 消息 |
| 易碎性 | 3 个功能提交之后的 6 个提交里，有 4 个在修日志功能自身的问题：latched 大消息让小分片反复开包、暂停时钟下分片读取顺序、规划取消与证据缺失的区分、测试发现规则 |
| 与本方案的耦合 | 控制快照的字段对应 fix 分支的内部实现（原路偏移预算、输入时钟与保持、参考时间、航点索引），本方案不移植这些（D9），消息必须重新设计 |
| 维护成本 | 自定义消息一旦写进 rosbag 就成了对外格式，改字段要考虑兼容；离线检查工具要跟着状态机一起维护 |

**结论：** 对"可开启、可配置路径、记录状态和模式变化"这个需求来说过于复杂，不移植。按第 9.2 节实现：生产代码预计约 300～350 行（核心事件生成、写日志线程、接线、查看脚本），测试约 150 行。本方案的单一 `step()` 让所有转换集中在一处，这是能做到这么小的前提。

**沿用的做法：**
- 启动时记录全部生效参数（`config` 事件）；
- 路径规则：留空用 `~/.ros` 下的默认目录，非空必须是绝对路径；
- 只保留最近若干次运行的日志；
- 记录规划输入，便于离线复现规划失败。

需要原始话题时，直接用标准 `rosbag record`（第 9.2 节的 `record_bag`），不写管理程序。
