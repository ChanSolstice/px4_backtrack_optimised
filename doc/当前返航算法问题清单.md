# 当前返航算法问题清单

## 1. 文档目的

本文档以当前 C++ 实现为准，记录 `px4_backtrack_optimised` 返航链路中已经确认的问题、条件性失效模式及其代码依据，作为后续修复、评审和实飞验收的统一基线。

- 审计日期：2026-08-27
- 审计基线：`dev` 分支提交 `79f05d6`
- 审计范围：CH7 触发、轨迹生成、yaw 处理、setpoint 发布、rejoin、fallback、模式切换、降落和运行健康监控
- 依赖范围：同时检查当前工作区中的 `../trajectory_core` 实际实现
- 本文档只描述问题，不包含代码修改

严重等级约定：

- **Critical**：可能直接破坏核心控制指令、阻断降落，或形成高风险失控链路。
- **High**：能够显著破坏返航连续性、终止正确性或路径安全性。
- **Medium**：在特定条件下导致状态错误、流程卡住、性能下降或退化行为异常。
- **Low**：以诊断性、可维护性或边界健壮性问题为主。

## 2. 总体结论

当前问题可以归纳为四组根因：

1. **setpoint 协议错误**：`PositionTarget.type_mask` 与注释及控制意图不一致，导致速度前馈和 rejoin 速度指令被屏蔽。
2. **时间进度与空间状态不闭环**：轨迹按 ROS elapsed time 推进，实际飞机只参与偏离判定，不决定轨迹进度和完成状态。
3. **航向语义与规划顺序错误**：返航位置逆序但 yaw 原样复用；未经最终平滑的 yaw 空间差分提前参与速度限制。
4. **状态机和退化流程活性不足**：模式请求缺少确认和重试，状态转换存在空目标窗口，fallback 与失败路径可能永久卡住。

已观察到的“走走停停”和“航向接近触发时方向”能够由当前代码直接解释：

```text
错误 type_mask
  -> 速度前馈失效
  -> 飞机落后按时间移动的位置目标
  -> 持续越过 rejoin 阈值
  -> 冻结、回拉、恢复
  -> 可能形成 ReturnActive/ReturnRejoin 循环

位置点逆序 + yaw 原样复用
  -> 返航位置反向运动
  -> 机头继续保持去程航向
  -> 表现为倒车返航
```

## 4. 详细问题说明

### 4.1 BT-CTRL-001：`PositionTarget.type_mask` 错误

正常轨迹、rejoin 和固定点悬停在无加速度输出时使用：

```cpp
target.type_mask = 0x0038;
```

相关位置：

- `src/application/backtrack_usecase.cpp`：轨迹 setpoint 和 rejoin setpoint
- `src/domain/state_machine.cpp`：固定点 setpoint
- `src/adapters/ros_publishers.cpp`：直接复制 `type_mask` 和全部目标字段

`0x0038` 实际由 `IGNORE_VX | IGNORE_VY | IGNORE_VZ` 组成，并不是代码注释所写的 `IGNORE_AFX | IGNORE_AFY | IGNORE_AFZ`。当前 `enable_output_acc=false` 时产生以下结果：

- trajectory_core 计算出的速度前馈被 PX4 忽略；
- rejoin 计算的最大 `0.3 m/s` 回拉速度同样被忽略；
- publisher 将空加速度写为零，但加速度字段没有被 mask；
- 飞机主要依赖不断移动的位置目标进行追踪，更容易产生相位滞后。

“零加速度”在此是零加速度前馈，不等同于把飞机的物理加速度限制为零；实际滞后量也不能仅根据代码固定为某个数值。

### 4.2 BT-ARCH-001：轨迹进度仅由时间决定

`TrajectorySession::evaluate()` 使用：

```cpp
t_progress_ = current_walltime - t_start_walltime_;
```

这里的时间是 ROS 时间，不是进程 CPU 时间。轨迹推进不使用：

- 当前位置在轨迹上的投影；
- 最近弧长或最近轨迹时间；
- 实际沿轨速度；
- 位置、速度跟踪误差反馈。

因此目标会按预定时间继续前进，实际飞机只在 rejoin 判断中被动参与。

### 4.3 BT-CTRL-002：可能形成 rejoin 极限环

当前配置为：

- 进入距离：`0.5 m`
- 进入持续时间：`0.25 s`
- 退出距离：`0.2 m`
- 退出持续时间：`0.10 s`
- rejoin 最大速度：`0.3 m/s`

当前实现已经具备进度冻结和距离滞回，所以 rejoin 极限环不是无条件必现。但在速度前馈失效、风扰、控制器响应慢或轨迹局部速度较高时，可能出现：

```text
ReturnActive
  -> 时间目标领先实际位置超过 0.5 m
  -> ReturnRejoin，冻结轨迹并回拉冻结点
  -> 进入 0.2 m 后恢复 ReturnActive
  -> 时间目标再次前进并重新产生滞后
```

该链路与实飞“飞一段、停一下、再继续”的现象高度一致。是否已经在某次飞行中形成极限环，应以 `/px4_backtrack/state` 和 `Deviation detected` 日志确认。

### 4.4 BT-SAFE-001：完成条件不验证物理到达

正常轨迹完成条件只有：

```cpp
t_progress_ >= traj_->duration()
```

没有检查：

- 与返航终点的最终位置距离；
- 当前位置速度是否已经收敛；
- yaw 和 yaw rate 是否已经收敛；
- 最终条件是否持续满足。

持续大距离受阻时通常会先触发 rejoin 并冻结时间，因此不能简单表述为“任何受阻都会在半路耗尽时间并降落”。仍然存在以下风险：

- 最终误差没有超过 `0.5 m` 时直接完成；
- 误差刚越过阈值但尚未持续满 `0.25 s` 时先完成；
- 飞机仍具有明显速度时进入降落前悬停；
- 非有限输入导致距离比较失效时，时间仍可能继续推进。

### 4.5 BT-YAW-001：返航 yaw 语义错误

`TrajectorySession::generate()` 反转航点索引后，直接复用录制 yaw：

```cpp
waypoints.emplace_back(pt.position, pt.yaw, t_new);
```

trajectory_core 后续执行 yaw unwrap、插值、平滑、末端保持和角速度限制，但不会：

- 按返航轨迹切线计算航向；
- 对去程航向增加 `pi`；
- 令机头朝向当前返航目标点。

因此当前算法的确定行为是“位置沿路径反向运动，机头按去程航向反向回放”。若去程 yaw 基本不变，返航将表现为倒车飞行。

### 4.6 BT-YAW-002：rejoin 和完成条件对 yaw 失明

`RejoinPolicy` 的进入和退出判断只使用三维位置距离，不包含 yaw 或 yaw-rate 误差。轨迹完成条件同样不检查 yaw。

这不表示底层姿态控制完全失效：正常 setpoint 仍包含 yaw/yaw_rate，PX4 会尝试追踪它们。准确问题是：

> yaw 偏差不会触发 rejoin，也不会阻止轨迹完成。

此外，当前更根本的问题是 BT-YAW-001：命令的目标 yaw 本身就不符合“机头朝向返航方向”的需求。

### 4.7 BT-PLAN-001：未经最终平滑的 yaw 差分限制速度

trajectory_core 的处理顺序为：

```text
重建 yaw_unwrapped 和 dyaw/ds
  -> 时间参数化，使用 dyaw/ds 计算 v_yaw
  -> 末端速度收敛
  -> yaw 平滑和 yaw-rate limiter
```

速度限制公式为：

```cpp
v_yaw = yaw_rate_max / abs(dyaw_ds);
```

因此录制 yaw 抖动会先形成较大的 `dyaw/ds` 并压低速度限制；后续 yaw 平滑无法恢复已经生成的速度剖面。forward/backward pass 会限制速度突变，所以不能仅根据代码断言必然出现瞬时速度断崖，但会产生不必要的局部速度谷、总时长增加和速度波动。

### 4.8 BT-STATE-001：AUTO.LAND 状态被映射成 `Recording`

当飞控模式为 `AUTO.LAND` 且仍 armed 时，状态机执行：

```cpp
enterState(State::Recording, input);
```

应用层的 `auto_land_yield_active_` 会抑制返航触发和 setpoint，因此不会在 AUTO.LAND 中重新接管控制。但仍有以下影响：

- `/px4_backtrack/state` 错误广播 `Recording`；
- `onOdomReceived()` 依据内部状态继续记录降落轨迹；
- 状态模型失去“降落已由外部接管”的明确语义。

### 4.9 BT-FALLBACK-001：严格球域导致进度活性不足

fallback 只有在当前位置进入 waypoint 的 `0.2 m` 三维球体时才推进索引：

```cpp
if (dist > reach_radius_m_) {
    return;
}
```

当前没有 waypoint 越过判定、线段投影、最近点跳转、到达超时或误差自适应。若位置控制长期稳定在 `0.21 m`，系统会持续命令同一个 waypoint，进度永久不推进。这是进度活性问题，而不是停止输出控制的“死区”。

### 4.10 BT-MODE-001：降落模式请求不闭环

`LandingTransition` 当前行为为：

```text
请求 POSCTL
  -> 不检查服务返回和实际模式
  -> 固定等待 1 s
  -> 请求一次 AUTO.LAND
  -> 进入 stage 2，之后不再请求
```

同时 `BacktrackNode` 调用 `SetModeClient::callSetMode()` 后丢弃返回值。若服务失败、请求被拒绝、实际模式没有切换，或请求被客户端节流，状态机仍认为流程已经推进。

进入 `LandingTransition` 后还会立即停止 setpoint；若此时仍处于 OFFBOARD 且 POSCTL 未成功，控制将依赖 PX4 自身的 offboard-loss 行为。

### 4.11 BT-SP-001：轨迹完成转换周期可能发布默认原点目标

`tickReturnActive()` 检测完成时先执行：

```cpp
current_setpoint_ = std::nullopt;
should_publish_setpoint_ = true;
```

随后切换到 `LandingHover`，但本周期不会再执行 `tickLandingHover()` 生成悬停目标。应用层此时看到 `should_publish_setpoint=true`，而 `computeSetpoint()`：

- 取不到状态机固定点；
- 当前状态已经不是 `ReturnActive` 或 `ReturnRejoin`；
- 最终返回默认构造的 `SetpointTarget`。

默认目标为位置原点、零 yaw、`type_mask=0`，所有字段均处于启用状态。该异常目标可能持续一个 20 Hz 控制周期。类似地，`ReturnPreOffboard -> ReturnActive` 的转换周期会额外残留一次固定点 setpoint。

### 4.12 BT-HEALTH-001：缺少运行健康监控

当前只对 RC 消息超时进行检测，没有检测：

- odom 是否停止更新；
- odom 位置、yaw 和时间戳是否为 NaN/Inf；
- `/mavros/state` 是否超时；
- MAVROS `connected` 状态；
- `ReturnActive`/`ReturnRejoin` 时是否仍处于 OFFBOARD。

odom 停止时，当前位置会保持旧值，而轨迹时间继续推进并最终进入 rejoin。飞控退出 OFFBOARD 时，内部轨迹同样继续推进，但状态机不会主动恢复 OFFBOARD，也不会冻结或中止会话。

### 4.13 BT-FALLBACK-002：fallback 恢复从首 waypoint 重启

暂停恢复 fallback 时调用 `WaypointFallbackSession::restart()`，该函数直接执行：

```cpp
current_index_ = 0;
```

如果已经返航到中途，恢复后的目标会重新变成返航触发点附近的第一个 waypoint，飞机可能先沿反方向回到返航起点，再重复整段 fallback 路径。

### 4.14 BT-GEN-001：非法配置导致永久悬停

轨迹配置无效时，应用层只清除 `trajectory_generation_requested_`，不进入 fallback、不触发降落，也不退出 `ReturnPreOffboard`。

此后 `trajectory_ready` 永远为 false，状态机会持续发布锁定位置，并在需要时继续请求 OFFBOARD，形成永久固定点悬停。

### 4.15 BT-CORRIDOR-001：走廊超限仍执行

trajectory_core 检测到拟合轨迹超过 `max_deviation_m` 后，只设置 warning flag，最终状态仍为 `SUCCESS`。返航侧收到结果后同样只打印告警并接受轨迹。

如果原始返航路径承担避障或安全走廊约束，超限轨迹继续执行会破坏该约束。

### 4.16 BT-RT-001：控制线程存在同步阻塞点

20 Hz timer 调用链中同步执行：

- 轨迹生成；
- 全轨迹采样；
- waypoint 和 trajectory CSV 写盘；
- RViz MarkerArray/Path 大消息构造和发布；
- `/mavros/set_mode` 同步服务调用。

这些操作会阻塞同一个 ROS spin 线程，延长 setpoint 发布间隔。CH18 流程可能已经在 `Ch18HoverWait` 中进入 OFFBOARD，因此后续同步生成和 debug IO 的实时性风险更高。

### 4.17 BT-DATA-001：数据和配置校验不足

当前还存在以下健壮性缺口：

- 录制缓存没有最大点数、最大时长或淘汰策略；
- 录制只按时间节流，不过滤非有限位置/yaw；
- trajectory YAML 解析会静默忽略已知字段的转换异常；
- 未知或拼错的 YAML key 不报错，继续使用默认值；
- 返航侧未统一验证 `publish_hz`、`record_max_hz`、阈值和持续时间参数的合法范围。

长航时记录会增加轨迹生成、CSV 和 RViz 消息开销；错误配置也可能在没有明确启动错误的情况下改变实际算法行为。

## 5. 已修复、不应重复归因的问题

仓库中的历史 Bug Report 记录过若干严重问题。当前实现已经包含以下修复，后续排查不应继续把它们当作当前主因：

- ReturnActive/ReturnRejoin tick 已显式清理固定点 setpoint；
- 进入 rejoin 时会冻结轨迹进度，退出时恢复；
- rejoin 控制目标与退出判据均使用同一个冻结进度点；
- rejoin 进入和退出已经加入持续时间判定；
- 轨迹生成前已经加入空间抽稀，停顿点云得到一定压缩；
- 当前 trajectory_core yaw-rate limiter 已限制单步积分不越过参考 yaw。

这些修复降低了历史问题的影响，但没有消除本文所列的协议、进度闭环、航向语义和状态机问题。

## 6. 修复优先级建议

建议按以下顺序推进后续代码修改：

1. **P0：控制协议和模式安全**
   - BT-CTRL-001：修正所有 PositionTarget mask；
   - BT-MODE-001：模式请求增加确认、重试和超时；
   - BT-SP-001：消除状态转换周期的默认零目标。
2. **P1：轨迹执行闭环**
   - BT-ARCH-001、BT-CTRL-002：重新定义轨迹进度与 rejoin 协作；
   - BT-SAFE-001：增加终点位置、速度、yaw 到达条件；
   - BT-HEALTH-001：增加 odom、state、OFFBOARD 健康监控。
3. **P1：航向和速度规划**
   - BT-YAW-001：明确返航航向策略；
   - BT-YAW-002：定义 yaw 是否参与完成与异常判断；
   - BT-PLAN-001：以最终 yaw 参考生成速度约束。
4. **P2：退化和失败流程**
   - BT-FALLBACK-001、BT-FALLBACK-002；
   - BT-GEN-001、BT-CORRIDOR-001；
   - BT-STATE-001。
5. **P2：实时性和健壮性**
   - BT-RT-001、BT-DATA-001。

## 7. 后续验收重点

后续修复至少应覆盖以下验证：

- 发布消息的 type mask 与 position/velocity/acceleration/yaw/yaw-rate 意图一致；
- 正常跟踪时不反复进入 ReturnRejoin；
- 风扰或人为阻挡后，轨迹不会继续按时间跑离实际飞机；
- 未满足终点位置、速度和 yaw 条件时不会进入降落；
- 返航 yaw 与选定策略一致，不再无条件复用去程 yaw；
- POSCTL/AUTO.LAND 请求失败时能够重试并保持安全 setpoint；
- 任意状态转换周期都不会发布默认原点目标；
- odom/state 超时或退出 OFFBOARD 时进入明确的安全状态；
- fallback 能处理稳态误差、越过 waypoint 和暂停恢复；
- corridor 超限、非法配置、同步任务超时均有确定的失败策略。
