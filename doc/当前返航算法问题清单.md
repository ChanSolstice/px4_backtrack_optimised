## 2. 已澄清的返航航向需求

返航需求不是“把去程 yaw 统一增加 180°”，而是：

1. 位置路径按照录制轨迹逆序；
2. 机头朝向返航轨迹的实际飞行方向；
3. 航向应由返航轨迹的水平切线或水平速度计算，例如：

   ```text
   yaw_ref = atan2(v_y, v_x)
   ```

4. 当水平速度或切线长度接近零时，应保持最近一个有效的切线航向，避免终点处由零速度产生未定义 yaw。

因此，以下两种做法都不满足需求：

- 逆序位置后直接复用录制时的 yaw；
- 不考虑路径形状，对全部录制 yaw 简单统一加 `pi`。

对于曲线、侧飞录制或录制过程中主动转头的情况，历史 yaw 与返航切线并不存在固定的 180° 关系。原文档只指出“复用去程 yaw”错误，但没有完整写出“以返航切线为约束”，属于需求描述疏漏。

### 3.1 FIX-01：修正所有 PositionTarget mask

修复前，正常轨迹和 rejoin 在无加速度输出时使用：

```cpp
target.type_mask = 0x0038;
```

代码位置：

- `src/application/backtrack_usecase.cpp:462-472`
- `src/application/backtrack_usecase.cpp:478-492`
- 固定点目标还使用了同类裸数值，见 `src/domain/state_machine.cpp`

`0x0038` 对应 `IGNORE_VX | IGNORE_VY | IGNORE_VZ`，不是注释所写的忽略加速度。直接结果是：

- trajectory_core 生成的速度前馈被 PX4 忽略；
- rejoin 的回拉速度也被忽略；
- 未提供加速度时，加速度字段反而仍处于启用状态并以零值发送。

这能直接造成跟踪响应迟缓，并显著增加位置误差触发 rejoin 的概率。代码本身不能证明固定“滞后约 1 m”，该数值必须由飞行日志确认。

实现结果：无加速度时改用命名掩码 `0x01C0`，只忽略 AFX/AFY/AFZ，保留位置、速度、yaw 和 yaw-rate，并增加固定点及正常轨迹输出测试。

### 3.2 FIX-02：按返航切线生成 yaw

修复前，`TrajectorySession::generate()` 在反转位置索引后直接复用录制 yaw：

```cpp
waypoints.emplace_back(pt.position, pt.yaw, t_new);
```

代码位置：`src/domain/trajectory_session.cpp:98-117`。

后续 trajectory_core 只会对输入 yaw 做 unwrap、插值、平滑和角速度限制，不会把它改成返航路径的切线方向。因此修复前实现无法保证机头朝向返航飞行方向。

实现结果：正常轨迹和 waypoint fallback 统一由逆序路径水平切线生成 yaw；垂直段、重复水平点和终点沿用邻近有效方向，完全没有水平运动时才使用触发时 yaw。没有引入额外航向策略配置。

### 3.3 FIX-03：消除状态转换周期的默认 setpoint

修复前，`tickReturnActive()` 检测完成时：

```cpp
current_setpoint_ = std::nullopt;
should_publish_setpoint_ = true;
enterState(State::LandingHover, input);
```

代码位置：`src/domain/state_machine.cpp:296-310`。

同一 tick 不会再次执行 `tickLandingHover()`。应用层随后调用 `computeSetpoint()` 时，当前状态已经不是 `ReturnActive`，又没有固定点目标，最终返回默认构造的 `SetpointTarget`：位置、yaw 和 mask 均为零值。该错误目标可能发布一个 20 Hz 周期。

实现结果：进入 `LandingHover` 时立即构造当前位置 hold setpoint，并增加状态转换测试覆盖位置、yaw 和 mask。

### 3.4 FIX-04：使降落模式切换形成最小闭环

修复前，`LandingTransition` 的逻辑是：

```text
请求 POSCTL
  -> 不确认实际模式，等待 1 s
  -> 请求一次 AUTO.LAND
  -> 之后不再请求
```

代码位置：

- `src/domain/state_machine.cpp:355-395`
- `src/backtrack_node.cpp:140-143`

状态机会在发出请求后直接推进阶段，节点也丢弃 `callSetMode()` 的返回结果。如果服务失败、飞控拒绝请求或实际模式没有改变，流程不会自行恢复。

实现结果：以实际 `mode` 驱动 POSCTL/AUTO.LAND 阶段并按现有 1 秒间隔重试；仍处于 OFFBOARD 时持续发布安全 hold setpoint。服务单次失败不再使流程永久越过请求阶段。

### 3.5 FIX-05：完成前增加终点位置验收

修复前，正常轨迹完成条件只有：

```cpp
return t_progress_ >= traj_->duration();
```

代码位置：`src/domain/trajectory_session.cpp:182-213`。

rejoin 会在明显偏离时冻结进度，因此“任何受阻都会在半路耗尽时间并降落”不是准确结论。但是在终止时刻误差尚未达到 rejoin 触发条件，或进入阈值但未满足持续时间时，仍可能直接进入降落阶段。

实现结果：时间结束后还需实际位置进入返航终点容差，当前复用 `rejoin_success_dist_m`，否则继续执行终点跟踪和既有 rejoin 判断。

首轮不把速度、yaw、轨迹投影或空间弧长都加入完成条件。机头朝向应由 FIX-02 保证；是否需要终点速度门限，应依据飞控验收结果再决定。

### 4.1 V-01：不要先重写时间推进和 rejoin

当前 rejoin 已经具备：

- 进入阈值 `0.5 m` 与退出阈值 `0.2 m` 的滞回；
- 进入/退出持续时间；
- 进入时冻结轨迹进度；
- 回拉目标与退出判断使用同一冻结点；
- 成功后从冻结进度恢复。

因此，反复 rejoin 是可能发生的闭环现象，但不是代码上无条件成立的“死循环”。应验证速度前馈恢复后是否仍反复越过阈值。当前不建议引入最近点投影、空间弧长推进或自适应时钟。

### 4.2 V-02：yaw 与速度剖面的耦合需要数据确认

trajectory_core 当前先用 `dyaw/ds` 限制速度，再执行最终 yaw 处理：

- `../trajectory_core/src/generator.cpp:221-284`
- `../trajectory_core/src/time_parameterization.cpp:47-58`

这会让输入 yaw 抖动具有压低局部速度的可能。但 forward/backward pass 会继续约束速度变化，不能只根据处理顺序断言一定产生实飞中的“断崖式骤降”。FIX-02 已改成切线 yaw，输入 yaw 的性质也随之改变，应在新轨迹数据上重新验证。

### 4.3 V-03：fallback 当前行为不应先按缺陷重构

fallback 使用固定球域推进，并且 `restart()` 从首 waypoint 开始。两者均有明确实现，其中“从头恢复”还有现有单元测试覆盖。它们是否违反产品需求尚未被证明，而且 fallback 只在轨迹生成退化时启用。

只有在退化模式被实际触发并观察到永久不推进或错误回头后，才需要讨论越过判定、最近点恢复或超时策略；不应预先同时加入动态半径、跳点、投影和超时机制。

### 4.4 V-04 至 V-06：先测量或确认策略

- 同步工作确实运行在控制回调链中，但没有耗时超过 50 ms 的证据；先打点测量。
- 当前只检查 RC 超时，健康监控可以增强，但不是“走走停停”和错误航向的已证实根因；若需要，先从 odom freshness 这一项开始。
- trajectory_core 将 `CORRIDOR_EXCEEDED` 明确定义为“轨迹仍可用”的 warning。是否改为硬失败属于任务安全策略，不是当前实现自相矛盾。

## 5. 当前不列为修复项

为避免多余、冗杂的防御性设计，本轮不包含：

- 用空间投影、弧长或自适应时间全面替换现有时间参数化执行；
- 把 yaw 误差同时加入 rejoin 触发和轨迹完成条件；
- 为所有消息建设通用 health-monitor 子系统；
- 为 fallback 同时增加动态半径、跳点、投影、超时和最近点恢复；
- 将同步逻辑整体迁移到 worker、队列或并发框架；
- 无条件把 corridor warning 改成轨迹生成失败；
- 建设通用配置回退、NaN、缓存容量和 YAML schema 框架；
- 修改 AUTO.LAND 时内部状态回到 `Recording` 的现有语义。

其中 AUTO.LAND 映射为 `Recording` 虽然状态名称不够直观，但当前实现会通过 `auto_land_yield_active_` 抑制控制输出，并且单元测试 `AutoLandHasGlobalPriorityAndYieldsControl` 明确验证了这一行为。除非外部消费者要求状态话题准确表达“正在降落”，否则它不是本轮控制问题。

## 6. 已经修复、不应重复归因的问题

当前仓库已经包含以下历史修复：

- ReturnActive/ReturnRejoin tick 会清理旧的固定点 setpoint；
- rejoin 会冻结并恢复轨迹进度；
- rejoin 控制目标与退出判据使用同一冻结目标；
- rejoin 进入和退出均有持续时间判定；
- 轨迹生成前已有空间抽稀；
- yaw-rate limiter 已避免单步积分越过参考 yaw。

后续分析不应再次把这些历史问题当作当前根因。
