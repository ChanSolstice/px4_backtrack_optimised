# 双仓库架构与运行边界审核

## 1. 审核范围与结论

审核日期：2026-09-07。依据 `/home/channing/Drone/AGENTS.md`，以实际参与构建的代码、配置和测试为准，优先正确性、简单性和可靠性，不因假设风险增加通用框架或重复保护。

| 仓库 | 审核分支 | 审核基线 |
| --- | --- | --- |
| `px4_backtrack_optimised` | `refactor/arc-length-path-following` | `b0222e6` |
| `trajectory_core` | `refactor/arc-length-trajectory-core` | `fb959e4` |

结论：架构方向合理，职责基本清晰，弧长跟随主链路适合当前逆序返航需求；但控制权、输入有效性和约束契约尚未闭合。目前可定位为已验证场景下运行的返航系统，不能把已有场景测试通过等同于任意输入、路径和外部模式下都有完整保障。没有推倒重构的必要。

本报告是两个仓库共享的审核记录，正文只维护在本文件。它记录审核意见，不代表已实施修复；以下问题均待处理或待决策。本次文档整理没有修改算法，也没有新增飞行验收结果。

## 2. 架构评价

| 模块 | 实际职责 | 评价 |
| --- | --- | --- |
| `trajectory_core` | 分段几何、速度规划、航向处理、只读轨迹查询 | 算法独立于 ROS，单独验证与复用的边界合理 |
| `TrajectorySession` / `RejoinPolicy` | 实际位置投影、单调进度、预瞄与回归策略 | 任务策略位于应用侧，没有混入通用几何库 |
| `BacktrackUseCase` / 状态机 | 触发、任务编排、状态与控制输出 | 主链路可追踪，但转换条件分散于两处，必须联合阅读 |
| ROS adapters / 节点入口 | 消息转换、模式请求、20 Hz 调度 | 通信边界明确，但阻塞操作与控制发布共用单线程 |

应保留的设计：库只在调用方给定区间内进行无状态投影；应用管理搜索窗口、进度单调性和完成判据。Hermite 投影的固定迭代上限及确定性并列仲裁也有利于行为预测。

可局部整理的耦合：UseCase 直接依赖具体调试发布器，RC 接收直接读取 ROS 时间，部分领域实现使用 ROS 日志。无需为架构纯粹性增加接口、工厂或新框架；在相关功能修改或测试确有困难时再收敛边界。

| 编号 | 问题 | 责任仓库 | 证据 | 顺序 |
| --- | --- | --- | --- | --- |
| AR-01 | 控制输入无新鲜度判定，旧状态仍可参与控飞 | backtrack | 代码确认 | 优先 |
| AR-02 | 外部退出 OFFBOARD 后仍推进任务并可能请求降落 | backtrack | 实际状态机离线复现 | 优先 |

| AR-05 | 实际弧长推进及 Rejoin 限速与名义 yaw rate 未同步 | 两仓库接口 | 代码与策略离线复现 | 后续 |
| AR-06 | 配置解析静默忽略错误，校验不完整 | 两仓库配置边界 | 非法配置离线复现 | 优先 |

## 4. 问题详情

### AR-01：输入新鲜度与失效语义

`onOdomReceived()` 保存位置、速度和 yaw，时间戳仅传给录制缓存，没有作为控制输入接收时间保存。飞控状态向 UseCase 只传 `armed/mode`，没有连接状态或新鲜度信息。

返航过程中 odometry 停止更新，节点仍会发布目标。弧长可能不再推进，但最后目标速度与 yaw rate 不一定为零；应用无法区分飞机停住与定位数据失效。投影失败后进入 Rejoin 并保留目标，也不等于零速度悬停：目标仍通过回归策略输出。

依据：[输入接收](../../src/application/backtrack_usecase.cpp) 的 `onOdomReceived()` / `onStateReceived()`、`handleTrajectoryProgress()` / `computeSetpoint()`；[订阅边界](../../src/adapters/ros_subscribers.cpp)。

最小建议：在输入边界统一检查数据有效性、新鲜度，并定义失效时的输出和恢复条件。不要在每个数学函数里重复加一套状态保护，也不要在缺乏有效位置时随意构造“当前位置悬停”。

验收重点：返航中暂停 odometry、持续收到旧时间戳、输入非有限数据；确认是否仍发布运动前馈，以及恢复后是否遵守既定策略。当前只做代码核查，未做这些场景的 SITL 验收。

### AR-02：外部模式退出后的任务控制权

状态机对 `AUTO.LAND` 全局让步，但 `ReturnActive` 没有检查模式是否仍为 OFFBOARD。任务空间进度更新也没有这个门槛。

实际状态机离线复现：

```text
ReturnActive 时输入 POSCTL：state=ReturnActive，publishing=1
随后输入 trajectory_finished=true 并经过悬停等待：
state=LandingTransition，request=AUTO.LAND
```

第二步是显式注入完成条件，代表人工接管后继续到达任务终点等情况，不代表一切 POSCTL 接管都会立即降落。

依据：[状态机](../../src/domain/state_machine.cpp) 的 `tickReturnActive()`、`tickLandingHover()`、`tickLandingTransition()`；[进度更新](../../src/application/backtrack_usecase.cpp) 的 `handleTrajectoryProgress()`。

最小建议：明确执行态中非本任务请求的模式退出应暂停还是终止；恢复须通过明确入口。优先复用已有 `Paused`，并联合核查降落阶段的人工接管语义。

验收重点：Active/Rejoin 时人工切换模式、完成条件随后成立、OFFBOARD 意外退出、明确恢复，以及本任务主动切换 POSCTL 的降落链路。

### AR-03：终点 yaw 球域不等于路径末段

`applyYawHold()` 遍历全部路径点，只要距终点不超过 `r_yaw_hold_m` 就覆盖为终点 yaw；没有剩余弧长或终段条件。默认半径为 1 m。

用当前返航切向 yaw 函数及仓库配置生成路径 `(0,0) → (0.5,0) → (0.5,0.5)`：起始输出 yaw 为 90°，前段速度方向为 0°，前段输出 yaw 仍为 90°。整条路径都在终点球域内，正常的短 L 型路径即可复现，并不限于闭合八字。

依据：[航向处理](../../../trajectory_core/src/yaw_processing.cpp) 的 `applyYawHold()` / `processYaw()`；[返航切向估计](../../src/domain/path_yaw.cpp)。

最小建议：先把终点 yaw 保持限定到真正的路径末段。另外，当前 yaw 来自输入折线切向，经重映射、平滑和限速后输出，并不严格等于最终几何的瞬时切向；应明确“朝向飞行方向”的允许偏差与例外（竖直段、近零速、末端保持、横向回归）。

验收重点：短 L 型、路径中途经过终点附近、起终点重合、末段弯曲，检查 yaw 与最终路径速度方向的夹角，而不仅检查 yaw rate 数值上限。

### AR-04：轨迹约束与查询的一致性

| 子项 | 实际实现/离线结果 | 影响边界 |
| --- | --- | --- |
| 竖直加速度参数 | `az_up_max/az_down_max` 仅在配置声明、校验和读写中使用，没有参与规划约束 | 不能把这些参数视为已落实的物理限制 |
| 时间查询导数 | `s(t)` 与 `v(s)` 分别线性插值；5 m 直线 `t=0.01 s` 时位置差分速度约 0.271163 m/s，返回速度为 0.010 m/s | `evaluate(t)` 的位置导数不等于返回速度 |
| 极短路径 | 0.1 m、首尾速度为零、`ds_m=0.15` 时生成成功，中点速度为零而名义时长为 2 s | 两个零速节点仍靠时间积分下限产生有限移动时间 |

竖直验证：将上下行加速度参数由 1.0 改为 0.01 m/s²，5 m 竖直路径输出时长均为 22.2905 s，报告最大竖直加速度仍约为 0.750189 m/s²。该报告是离散估算，不是实飞测量。

依据：[规划](../../../trajectory_core/src/time_parameterization.cpp)、[查询插值](../../../trajectory_core/src/trajectory_impl.hpp)、[配置](../../../trajectory_core/src/config.cpp)。

当前应用按弧长查询，且结束位置容差为 0.2 m，因此时间查询问题不能直接等同于旧版 wall-time 顿挫重现，0.1 m 情况也不应直接推断为应用必然卡死。但独立轨迹库的公开契约仍需修正。

最小建议：统一区间运动模型；明确极短路径的可行输出或失败语义；对未实现的约束选择落实或明确标注不支持。不要先添加复杂求解器。

验收重点：数值差分核对 `dp/dt=v`、约束参数改变确实影响输出、只有两个重采样节点的短路径，以及现有短路径修复不回归。

### AR-05：名义 yaw rate 与实际进度不一致

库返回名义时间剖面的 yaw rate，应用却按实际位置更新弧长。Rejoin 修改速度向量，仍原样保留 yaw rate。策略离线验证中，速度从 1.0 降为 0.3 m/s，yaw rate 仍为 0.6 rad/s。

当目标弧长暂时不变时，yaw 目标也不变，却可能持续发出非零 yaw rate。这证明目标与前馈的一致性缺少保证，不证明飞机必然发生扭动。

依据：[yaw rate 查询](../../../trajectory_core/src/trajectory_impl.hpp) 的 `yawRateFromArcLength()`；[Rejoin 限速](../../src/domain/rejoin_policy.cpp) 的 `applyRejoinLimits()`；[目标发布](../../src/application/backtrack_usecase.cpp) 的 `computeSetpoint()`。

最小建议：先定义 yaw rate 对应名义速度还是在线目标进度变化率，再决定转换方法与是否启用前馈；单纯增加另一个限幅器不能消除语义差异。位置预瞄叠加速度前馈属于引导方式，名义 `v_max` 和 Rejoin 前馈限速均不能直接当作实际飞机速度硬上限。

验收重点：固定目标弧长、曲线上的慢速推进、Rejoin 降速/恢复，联合检查连续 yaw 目标差分和 yaw rate 字段，并通过 SITL 观察实际响应。

### AR-06：配置边界允许静默错误

`loadFromYaml()` 吞掉已知字段的解析异常。例如 `v_max: oops` 加载成功并使用库默认 2.0 m/s，而仓库正常配置为 1.0 m/s。`v_max=NaN` 也可通过目前的 `validate()`。应用侧没有集中校验发布频率、Rejoin 阈值关系等参数。

依据：[库配置](../../../trajectory_core/src/config.cpp)、[应用参数加载](../../src/infrastructure/config_loader.cpp)、[发布频率装配](../../src/backtrack_node.cpp)。

最小建议：启动时集中校验解析结果、有限数值和必要关系；错误报告具体字段并拒绝启动。无需让错误配置进入飞行期再增加一套 fallback。

验收重点：非法数字、非有限数值、非法布尔值、拼错字段和矛盾阈值；合法配置仍保持原行为。

### AR-07：RC 丢失事件被提前消费

`handleTriggers()` 在状态分支前调用边沿型 `checkRCLossEvent()`，但只有 Recording/Paused 等状态处理事件。等待录制期间已经触发的丢失会被锁存，进入 Recording 后不会再产生新边沿。

触发器离线验证：等待期 `event=1`，之后模拟进入录制期再次检查时 `event=0, lost=1`。状态消费路径由 UseCase 代码确认；这不是完整 ROS 用例。

依据：[事件消费](../../src/application/backtrack_usecase.cpp) 的 `handleTriggers()`；[边沿锁存](../../src/domain/trigger_evaluator.cpp) 的 `checkRCLossEvent()`。

最小建议：明确进入可响应状态时如何处理已经存在的故障电平，并保留一次性触发语义。不要简单把同一故障每周期重新触发。

验收重点：录制等待期发生 RC loss、进入 Recording 后仍未恢复、收到 RC 后再次丢失、飞行周期复位。未收到过 RC 时的启动保护需按既有需求保留。

### AR-08：控制调度与输入规模

单线程 `ros::spin()` 中，tick 同步生成轨迹并执行调试采样、文件导出；模式切换使用同步服务调用。部分几何生成步骤反复扫描整条折线，`seg_hint` 只改变搜索顺序，没有减少总扫描范围；录制缓存也没有任务规模上限。

本机以 `(0.1i, sin(0.01i), 0)` 构造路径，使用生产配置和返航切向 yaw 函数计时：

| 输入点数 | 本机生成耗时 |
| --- | --- |
| 200 | 约 1.47 ms |
| 1,000 | 约 18.10 ms |
| 3,000 | 约 156.72 ms |

计时包含构造航向输入与生成调用，不包含 ROS 调试导出或模式服务。这说明单次工作可能超过 20 Hz 的 50 ms 周期，不证明已触发 PX4 超时，也不代表目标机性能。

依据：[节点调度](../../src/backtrack_node.cpp)、[同步生成与调试](../../src/application/backtrack_usecase.cpp)、[同步模式调用](../../src/adapters/ros_services.cpp)、[全折线扫描](../../../trajectory_core/src/math_utils.cpp)。

最小建议：确定最大录制时长、点数和路径长度，测量目标机最坏耗时；不满足预算时，再隔离一次性生成和阻塞 I/O。不要直接引入通用并发框架，也不要在没有同步设计时简单改成多线程 spinner。

## 5. 可以保留但必须说明的运行边界

| 机制 | 当前边界 | 审核意见 |
| --- | --- | --- |
| 局部投影、单调进度 | 避免远处自交分支跳转；不保证定位大跳变、密集小环或暂停后大范围移动都可正确恢复 | 保留简单策略，明确适用范围，必要时增加针对性验收 |
| 起始 yaw 目标阶跃 | 实际转速依赖 PX4 配置；应用没有起始 yaw 变化率限制器 | 可以成立，是否加限制器取决于跨配置一致性需求 |
| 无总时长自动降落 | 空间未完成不会因旧秒表耗尽而进入降落 | 不应为保证“必然退出”随意恢复时长到期降落 |
| 走廊超限 warning | 库仍可返回成功，应用记录 warning 后使用轨迹 | 属于软约束契约，不是严格走廊或避障保证 |
| WaypointFallback | 逐点位置目标、独立球域推进、恢复索引归零，不走正常轨迹起始 yaw 对准门槛 | 独立降级模式，不能宣称具有正常轨迹的连续性与约束 |
| 终点判定 | 正常轨迹检查剩余弧长、三维位置距离和水平速度 | 当前明确实现，不应宣称已经约束完整三维速度或 yaw |
| 路径平滑 | LINEAR + HERMITE_BLEND，不保证全路径加速度/jerk 连续 | 没有更高连续性需求时，不必重写为更复杂样条 |

“无法保证”不等于“必然发生故障”。只对实际需求覆盖不到且有代码/测试证据的问题安排修复，其他边界先明确产品使用条件。
